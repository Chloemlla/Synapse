## D1 — /tts 需要支持多提供商并存 + 用户切换（需求）

- **类型**：功能缺失（当前架构把「提供商」建模成单值）
- **位置**：
  - `src/config/ttsProviderConfig.ts:25-35`（`TtsProviderRuntimeConfig.provider` 是单值
    `TtsProviderId`）、`:358-416`（`buildTtsProviderPublicConfig` 只产出当前这一个提供商）、
    `:418-471`（`buildTtsProviderExecutionSnapshot` 按 `runtimeConfig.provider` 单路分支）
  - `src/tts/tts.provider-router.ts:24-44`（`resolveExecutionSnapshot(requestedModel, requestedVoice, frozen)`，
    请求侧没有任何「选哪个提供商」的入口）
  - `src/tts/tts.service.ts:123-129`、`src/tts/tts.pipeline.ts:293-303`（提交时冻结快照）
  - `src/controllers/ttsProviderController.ts:89`（公开配置只回单个 config）
  - 前端：`frontend/src/types/tts.ts`、`frontend/src/utils/ttsProviderConfig.ts:129-197`、
    `frontend/src/components/TTSForm.tsx:114-160,345-398`、`frontend/src/hooks/useTts.ts`
  - 管理端：`frontend/src/components/env-manager/TtsProviderConfigSection.tsx:176-242,294-308`、
    `frontend/src/components/env-manager/types.ts`
  - 后端管理端读写：`src/routes/admin/config.ts:165,175`、`src/services/runtimeConfigService.ts:2047`、
    `src/config/runtimeConfigDefaults.ts`
- **详细错误信息/现状**：管理员只能在后台选**一个**「当前提供商」，`/tts` 页面据此渲染唯一的
  模型/音色/格式集合，用户无法在多提供商之间切换。要让「同时展示多个 + 用户切换」成立，
  必须让运行时配置能表达「启用了哪几个」，并让生成请求能携带用户的选择。
- **建议改法**（最小可用形态，保持单提供商时行为完全不变）：
  1. `TtsProviderRuntimeConfig` 增加 `enabledProviders: TtsProviderId[]`；规范化：仅合法 id、去重、
     必含 `provider`、主提供商排第一；缺省回退 `[provider]`。`mergeTtsProviderAdminUpdate` 接受并
     合并该字段（缺省保留现值）。`runtimeConfigDefaults.ts` 给默认值。
  2. 抽出 `buildProviderPublicConfig(runtimeConfig, providerId, openAiDefaults)`，供三个分支共用；
     `buildTtsProviderPublicConfig` 继续返回**主提供商**的扁平结构（向后兼容旧前端包），并在
     **启用数 > 1 时**附加 `providers: TtsProviderPublicConfig[]`（否则不附加，保证单提供商时请求
     体逐字节不变）。跨提供商模型串味由既有 `isForeignTtsModelId` 兜住：非主提供商一律用其自带
     默认模型（openai→`openAiDefaults.model`、fish→`FISH_AUDIO_DEFAULT_MODEL`、edge→`EDGE_MODEL_ID`）。
  3. `buildTtsProviderExecutionSnapshot` 的 `input` 增加 `provider?: string`：命中
     `enabledProviders` 才采用，否则回落主提供商（**不抛错**——老客户端不带该字段必须照旧工作）。
  4. `resolveExecutionSnapshot` / `resolveProviderExecution` 增加 `requestedProvider` 参数，
     `tts.pipeline.ts` 把 `rawRequestPayload.provider` 透传下去。
  5. 前端：`TtsProviderPublicConfig` 增加可选 `providers?`；`normalizeTtsProviderConfig` 归一化每个
     子项（含回退成 `[主配置]`）；`TtsRequest` 增加 `provider?`；`TTSForm` 在 `providers.length > 1`
     时渲染切换控件，切换时把 model/voice/outputFormat 重置为该提供商的默认值，并在提交体里带
     `provider`；只有一个提供商时不渲染任何新控件。
  6. 管理端：加「启用的提供商」多选（openai/fish/edge），「默认提供商」保持单选且必须处于启用集合内。

## D2 — SPA 路径清单只覆盖 /admin 模块页（需求）

- **类型**：生成器覆盖面不足（同一缺陷类已修过一次）
- **位置**：`scripts/generate-admin-spa-paths.js:12`（只读 `adminModules.tsx`）、
  `src/routes/legacyApiRedirect.ts:302-304,438-441`、`src/generated/adminSpaModulePaths.ts`
- **详细错误信息/现状**：清单只由 `ADMIN_MODULE_LOADERS` 推导，因此只有 `/admin/<module>` 的整页
  导航会被放行给 SPA。`App.tsx` 里其余前端路由（如 `/transcribe`、`/store`、`/articles/:slug`、
  `/profile`…）若与旧 API 前缀重名，深链/刷新会被 308 到 `/api/...`。历史上 `/admin/ip-risk-logs`
  就是这么漏的。
- **建议改法**：生成器同时解析 `frontend/src/App.tsx` 的 `<Route path=...>`（只取静态段，忽略 `*`
  与含 `:` 参数的通配路由，参数路由取其静态前缀），产出**完整前端 SPA 路径清单**（与 admin 清单
  合并导出）；`legacyApiRedirect` 用该清单放行整页导航。**碰撞集
  （`frontendRoutesWithLegacyApiCollision`）必须仍然优先**，否则 `/admin/users`、`/policy` 等会静默
  丢掉选择页。CI 漂移闸门 `check:admin-spa-paths` 与既有测试同步更新。

## D3 — 转写失败：yt-dlp 退出码=1，B 站 412（缺陷）

- **类型**：外部反爬（缺失请求头）
- **位置**：`src/mediaTool/biliYtDlp.ts:210-241`（`buildArgs`）、`:257`（spawn）、`:313`（错误串联）、
  `src/mediaTool/types.ts:55-65`（`BiliOptions` 无 UA/Referer 字段）、`.env.example:150-152`
- **详细错误信息/现状**：`ERROR: [BiliBili] 1huYE6REHj: Unable to download webpage: HTTP Error 412:
  Precondition Failed`。`buildArgs` 只追加 `--cookies`（且仅当 cookie 文件存在）与下载/合并参数，
  **从不传 `--user-agent` / `--referer` / `--add-header`**；B 站 WAF 对无浏览器 UA 的请求直接 412。
  仅有的正确 B 站调用样例是 `src/services/bilibiliSyncService.ts:142-157`（显式带 Cookie + UA）。
- **建议改法**：给 yt-dlp 调用补浏览器 UA 与 Referer/Origin（`--user-agent`、
  `--add-header "Referer:https://www.bilibili.com/"`、`--add-header "Origin:https://www.bilibili.com"`），
  默认值写成常量并允许 `MEDIA_TOOL_YTDLP_USER_AGENT` 环境变量覆盖，同步 `.env.example`。
  **诚实标注**：受 IP 信誉影响的 412 未必只靠 UA 解决；CI 无法覆盖真实 B 站请求，本条修复
  无法由 CI 证明，需用户以真实链接复验。

## D4 — proxycheck 对外请求未落库（缺陷）

- **类型**：Mongoose 校验规则与数据自相矛盾 → `create()` 抛错被吞（**已定位，已修**）
- **位置**：`src/models/proxycheckLookupLogModel.ts:69`
  （`error: { type: String, required: true, default: "" }`，子文档 `:47` 的 `reason` 同型）
- **详细错误信息/现状**：`logLookup`（`src/services/ipRiskService.ts:166-189`）用
  `ProxycheckLookupLogModel.create(...)` 落库，而 **Mongoose 对 String 的 `required` 判据是
  「非空字符串」**——直接从本机装好的 mongoose 源码读到（`lib/schema/string.js`，8.17.1 与 9.0.0
  一致）：
  ```js
  SchemaString._checkRequired = v => (v instanceof String || typeof v === 'string') && v.length;
  ```
  同文件的文档注释也写明 “The `required` validator **will** fail for empty strings.”
  于是 `required: true` 与 `default: ""` 是一对自相矛盾的声明：**只要该字段的值是空串就一定校验失败**。
  恰好 `logLookup` 传的是 `error: input.error || ""`，而两条主路径根本不给 `error`：
  - `status: "ok"`（外呼成功，`:433-442`）→ `error: ""` → **校验失败**
  - `status: "cache"`（命中缓存，`logCachedLookup` `:236-260`）→ `error: ""` → **校验失败**
  - `status: "deduped"`（in-flight 合并）→ `error: ""` → **校验失败**

  只有 `failed` / `not_configured` / `quota_exhausted` 三条路径带上了非空 `error`，能正常落库。
  这正好是用户看到的现象——**每一次成功的 proxycheck 外呼都没有落库**；失败被
  `catch` 收敛成一行 `logger.warn("[IpRisk] Failed to persist proxycheck lookup log")`，面板上
  完全看不出来。
- **为什么之前排查判成「静态链路完好」**：只看调用点是否 `await`、字段是否齐全，
  没有把 schema 的 `required` 语义算进去；而 `src/tests/ipRiskDecision.test.ts:112-127` 里那条
  「`error: ""` 的行照样通过校验」（fixture `:121`）的断言本可以证伪——但后端 Jest 步骤当前是
  `continue-on-error`（ts-jest × typescript@7 跑不起来，`Tests: 0 total`），这条断言不会被执行，
  缺陷因此长期隐形。
- **修复**：`proxycheckLookupLogModel.ts` 去掉 `error` 与 decision 子文档 `reason` 上的
  `required: true`（保留 `default: ""`），并就地写明原因，防止再被加回去。
  **同型声明未被牵连**：`proxycheckRiskCacheModel.ts:47-60` 的 12 个 `required: true, default: ""`
  走的是 `findOneAndUpdate`/`updateOne`（Mongoose 的 update 默认不跑 validator），
  `configurationNoticeStateModel.ts:5` 同样只被 update 写，所以它们不受影响。
- **验证说明**：本条依 lib 源码语义 + 代码路径推导，**CI 无法证明**（后端 Jest 步骤不参与门禁且
  当前跑不起来）。`ipRiskDecision.test.ts` 里既有的空 `error` 断言就是这条修复的回归守卫，
  待 G13-01/02 恢复后有 CI 判据。

## D5 — 官方客户端登录仍显示「未知客户端」（缺陷）

- **位置**：`src/services/authSessionService.ts:352,370`（`listAuthDevices` 输出 `clientType`）、

  `client`/`clientName`/`appName`/`application`）、渲染点
  `frontend/src/components/user-profile/DeviceSessionsPanel.tsx:154`
- **详细错误信息/现状**：Android 客户端在登录与换令牌时确实带上了
  `X-Client-Name: Synapse-Client` 等头（`SynapseMobileLoginApi.kt:311-351` 的 `post()` 无条件套
  `clientMetadata()`），后端也确实把它规范化成 `clientType: "Synapse-Client"` 落库
  （`src/models/authSessionModel.ts:30-55`）。但前端 `normalizeDeviceSession` 的候选键列表里既没有
  `clientType` 也没有对应别名，`firstString` 全部落空 → 恒为 `未知客户端`。客户端 App 自身能正确显示，
  因为它读的是 `clientType`（`SynapseSecurityJsonMappings.kt:119-120`）。
- **建议改法**：`profileHelpers.ts:165` 的候选键加入 `clientType`（放在 `clientName` 之后、
  `appName` 之前），后端无需改动。
