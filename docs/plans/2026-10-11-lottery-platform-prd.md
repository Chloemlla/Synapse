## 1. 系统定位

不是「随机出奖」脚本，而是**营销中台**：玩法引擎 + 动态调控算法 + 全链路风控 + 权益履约 +
资金 / 库存对账 + 用户增长裂变。核心原则：

1. **表现与发奖解耦**：前端交互形式（转盘 / 九宫格 / 盲盒 / 集卡…）只负责「展示 + 触发」，
   发奖由后端统一引擎裁决，换皮不改算法。
2. **发奖零超卖**：三层库存防线 + 幂等 Request ID，任何一层抖动都不产生超发。
3. **可审计可追溯**：每次抽奖留随机数快照、落点权重、风控分、扣减流水，满足法律与财务核验。
4. **风控柔性对抗**：高危请求不报错、静默降级为空奖，抬高黑产逆向成本。
5. **失败可恢复**：异步履约走租约队列，Worker 崩溃由看门狗回收，不产生「永远处理中」。

## 2. 业务架构与状态流转

核心链路四步：**资格校验 → 概率判定 → 库存扣减 → 异步履约**。

```
[用户触发]
   │
   ▼
[基础校验] ── 活动状态 / 白黑名单 / 频次限制 ──► 失败：拦截并提示
   │
   ▼
[扣减抽奖机会] ── 原子操作 / 消耗积分或额度 ──► 失败：提示机会不足
   │
   ▼
[风控实时引擎] ── 设备指纹 / 行为画像 / IP 频率 ──► 风险：静默降级至低概率或空奖
   │
   ▼
[核心抽奖计算] ── 全量权重打乱 / 动态保底 / 预算与速率控制
   │
   ▼
[奖品库存扣减] ── 三层防线（内存标记 → Redis Lua → DB 正数约束）──► 售罄：降级垫底兜底奖
   │
   ▼
[结果落库 & 履约] ── 幂等 Request ID；异步任务队列（租约 + 看门狗）→ 外部发货
```

抽奖请求本身只产生「中奖意向 + 库存扣减 + 流水」，实物邮寄、卡密下发等耗时动作全部进异步队列。

### 3.2 奖池体系与出奖算法

- **纯权重随机（CSPRNG）**：`P_i = W_i / ΣW_k`，服务端 `crypto.randomInt`。`[x]`
  （语义已修正：`probability` 为绝对概率，概率和 < 1 的剩余区间即未中奖，不再补贴第一个奖品）
- **多奖池分层**：主奖池 / 新手·回归专属池 / 暗池（兜底空奖或低成本代币，用户无感知）。`[ ]`
- **伪随机平滑补偿**：未命中递增概率因子、命中后重置，防「极度脸黑」流失。`[x]`
  （`round.pseudoRandom = { increment, maxBonus }`，按未命中次数线性压随机值）
- **硬保底**：第 N 抽必中指定稀有度。`[x]`（`round.guarantee = { everyDraws, category }`；按本轮个人次数，
  必中该稀有度及以上，无符合条件的有库存奖品则回落普通抽取）
- **软保底**：超过 N 抽后稀有奖品概率线性递增。`[x]`（`round.softGuarantee = { startsAfterDraws, category, step }`，
  触发后必出该档，纯权重归一）
- **预算与速率控制（Pacing）**：贵重奖品按天/小时切配额，窗口未到或用尽 → 权重归零。`[ ]`
- **入参硬化**：时间可解析、概率 0-1、数量正整数、库存服务端初始化、id 去重。`[x]`

## 4. 技术高可用与鲁棒性

### 4.1 三层库存防线（绝对防超卖）

1. **内存快速拦截**：售罄标志位/布隆过滤器，应用层直接拒绝，不穿透下游。`[ ]`
2. **分布式原子扣减**：Redis 预热库存 + Lua 原子校验扣减 + Request ID 幂等。`[ ]`
   （现状：`sharedStateStore.withLock` 进程/共享锁实现，无 Redis 时降级。）
3. **数据库最终防线**：物理扣减带正数约束（`remaining > 0`），对账 Worker 兜异常。`[ ]`
   （现状：`pickPrize` 只选 `remaining > 0`，扣减在最新快照上做；缺显式 `WHERE remaining > 0`。）

### 4.2 高并发削峰与防穿透

- 活动配置 / 奖品图文 CDN 化、规则与基础数据 Redis 缓存。`[ ]`
- **中奖与履约解耦**：判定只返回意向，履约走异步队列。`[ ]`（队列基础设施已具备，见 §4.4）

### 4.3 资金与库存闭环对账

- **T+0 准实时**：每 5 分钟巡检「已发奖记录数 / Redis 消耗数 / DB 真实库存减量」偏离度。`[ ]`
- **T+1 离线**：每日凌晨核对财务出账、券总量与业务流水，出差异报表。`[ ]`

### 4.4 任务队列：租约模型 + 看门狗（本轮实施）

Express + MongoDB 轻量级任务队列（当前为 TTS 生成队列 `src/tts/tts.queue.ts` +
`src/tts/tts.storage.ts`，后续抽奖履约复用同一模式）。目标是杜绝「Worker 崩溃后任务永远
停在处理中」，同时防「重叠消费」。

**1）任务可见性与租约**

- 抢占时除置 `processing` 外写 `leaseExpiresAt = now + 租约时长` 与 `processingOwner`。`[x]`
- 每次抢占 `attempts += 1`（重试计数）。`[x]`
- **心跳续租**：长任务由 Worker 后台按 `租约/3` 周期刷新 `leaseExpiresAt`；Worker 挂则心跳中断、
  租约自然过期。`[x]`（本轮新增 `renewJobLease` + `startLeaseHeartbeat`）

**2）看门狗检测与抢占式回收**

- 独立低频巡检（现 5 分钟；`[决策]` 是否缩短到 30s～1min）。`[x]`
- 判定：`status=processing` 且 `leaseExpiresAt <= now`。`[x]`
- **原子复位**：多实例看门狗并发时，条件必须写进更新语句本身，只对「确实仍超时」的单条回滚为
  `queued`、清空 owner 与租约；不得 `find` 后再无条件 `updateMany`。`[x]`（本轮改为逐条
  `findOneAndUpdate` 条件更新，含 `status/leaseExpiresAt/attempts`）
- 未超限回 `queued` 重入公共池，其它健康 Worker 下一轮认领。`[x]`

**3）死信判定与分流**

- 最大重试次数（现 `TTS_MAX_ATTEMPTS = 3`；`[决策]` 3～5 取值）。`[x]`
- 达上限不再回 `queued`，直接置 `failed`（死信）并记录超时原因。`[x]`
- **告警**：进入死信时通知技术人员（见 §4.5）。`[x]`（`sendAdminAlert`，一轮回收合并一封）
- 保留原始现场供手动重放（任务记录不物理删除）。`[x]`

**4）重叠消费防护**

- **终态乐观锁**：`completeJob` / `failJob` 必须带认领时的 `processingOwner` 前置条件；不匹配
  （已被看门狗回收/转交）则拒绝写入，原 Worker 放弃终态与用户通知。`[x]`
  （本轮：不再忽略返回的 `null`，主动放弃 + 告警日志）
- **下游绝对幂等**：履约服务（积分/券码/扣减）必须用全局唯一抽奖流水号做幂等拦截，即使两个
  Worker 同时发起也只生效一次。`[ ]`

### 4.5 通知与告警通道

- **本部署只有邮件 + webhook**（**没有钉钉 / 企业微信**）。
- 邮件：发给 admin / superadmin 团队邮箱（与工单通知同一批收件人）。`[x]`
- webhook：配置 `ALERT_WEBHOOK_URL` 时 POST 结构化 JSON，未配置则跳过。`[x]`
- 告警只用于人工介入事件（死信、队列异常）；同一轮回收合并成一封摘要，不逐条轰炸。`[x]`

## 5. 关键接口约定（已实现部分）

- `GET /api/lottery/rounds/active` 等只读端点：普通用户视图不含参与者内部 userId，
  返回 `hasParticipated` / `participantCount` / `winnerCount`。`[x]`
- `POST /api/lottery/rounds/:roundId/participate`
  - 入参：`captchaToken|captchaProvider`（人机验证）、`requestId`（幂等键，≤64）。`[x]`
  - 幂等：同 `requestId` 重放直接返回上次结果；并发未完成 / 换轮次复用同一 id 被拒。`[x]`
  - 出参：`data` 为中奖记录；未中奖为 `null`。`[x]`
  - 多次抽奖 / 机会：按 `maxDrawsPerUser` 限制次数（`drawCounts`）、按 `chanceCost` 原子扣减机会。`[x]`
- `GET /api/lottery/chances`：机会余额（懒发放当日免费额度）。`[x]`
- `POST /api/lottery/chances/grant`（超管）：发放机会，写 `lottery.chances_grant` 审计。`[x]`
- 普通用户轮次视图附加：`maxDrawsPerUser` / `chanceCost` / `drawsUsed` / `remainingDraws`，不回 `drawCounts`。`[x]`
- 审计：每次抽奖写 `audit_logs`（`module=lottery`、`action=lottery.draw`），
  `detail` 含 `randomValue / prizeId / remainingAfter / requestId`。`[x]`
