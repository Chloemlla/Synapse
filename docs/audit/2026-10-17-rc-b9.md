### RC-39：文件任务沙箱 + 子进程看门狗

**改动文件**

    `checkUploadBudget` 用"最坏增量"在写盘**之前**拒绝；`inspectUploadedFile` **失败关闭**
    （stat 失败/非普通文件/空文件/超限/类型不符一律拒绝）。
  - 默认值：500MB / 5 个/任务 / 4GiB / 500 个文件；env
    `MEDIA_TOOL_MAX_FILE_BYTES`、`MEDIA_TOOL_MAX_FILES_PER_JOB`、
    `MEDIA_TOOL_USER_DIR_MAX_BYTES`、`MEDIA_TOOL_USER_DIR_MAX_FILES`。
- `src/mediaTool/http/transcribeUserHttp.ts`：上传前目录配额预检、落盘后复核；
  复核失败**删除刚写的文件**再回 4xx（不留孤儿文件，带稳定 code）。
- `src/mediaTool/runtime.ts`：`runTool`（`spawnSync`）加硬 `timeout`（env
  `MEDIA_TOOL_SYNC_TOOL_TIMEOUT_MS`，默认 120s）。原因：`spawnSync` 阻塞事件循环，
  异步看门狗在这段时间里不会 tick —— 同步调用只能用 `spawnSync` 自己的 timeout。
- 新增 `src/utils/processWatchdog.ts`
  - **只读目标子进程树**的 RSS：`/proc/<pid>/status` 的 `VmRSS` + 通过 `/proc/*/stat` 的
    ppid 建树求和；绝不读 `process.memoryUsage().rss`。
  - 超限（RSS 或时长）时：`observe` 只告警；`enforce` 只对**该进程树**发 SIGKILL
    （先杀后代再杀根）。计量不可用（非 Linux / 进程已退出 / `/proc` 不可用）时
    **不做内存击杀**，时长判据仍生效。
  - 默认：2GiB / 60 分钟 / `observe`；env `PROCESS_WATCHDOG_MAX_RSS_MB` /
    `PROCESS_WATCHDOG_MAX_DURATION_MS` / `PROCESS_WATCHDOG_MODE=enforce`。
- `src/mediaTool/biliYtDlp.ts`：`runYtDlp` 起子进程后挂看门狗，`close/error/取消` 时停止；
  触发时写入任务日志（观察期/已终止）。

**验证点**

- `auditB9CostControls.test.ts` 的「RC-39 文件沙箱」「RC-39 子进程看门狗」两组：
  目录配额、空文件/超大/类型/越界全部失败关闭；`VmRSS` 解析；enforce 只调用子进程
  `kill("SIGKILL")`；observe 不击杀；时长上限独立于内存判据。
- 人工：`getOccupancy...` 之外，`runYtDlp` 的 `stopKiller()` 同时停止看门狗（无 interval 泄漏）。

**挂起项 / 边界**

1. 非 Linux（本机 Windows 开发态）读不到 `/proc`：内存判据不可用（只记录一次告警），
   时长判据仍生效。生产镜像为 Linux，不受影响。
2. `spawnSync` 调用的工具只能靠 `timeout` 兜底（无法用异步看门狗）。
3. 管理端 `/api/admin/media-tool/upload` 已有类型白名单 + 400MB + 单文件限制，
   本批次未改（管理员可信域，且其行为已满足四道硬顶的前三道）。
4. 用户转写页的 `maxActiveJobs` **已存在**（设置页可改，默认 2），本批次未收紧到审计建议的
   「=1」—— 那是产品取值，且会改变现有用户体验，需 owner 决定；RC-30 的 per-user 上限
