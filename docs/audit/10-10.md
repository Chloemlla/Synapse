# 风控加固分析：账户标记、逐步验证与软删除（2026-10-10）

> 任务来源：用户要求「对普通用户 + 注册滥用做多方位全角度风控加强」，包含
> (a) 封禁账户，(b) **被标记的危险账户在前端每一次操作都弹人机验证、后端每一次操作都鉴别**，
> (c) 账户标记融入**历来登录 IP risk score**，(d) 用户在前/后端 profile 页面删除的**一律软删除**，风控仍可读。
>
> 第二轮补充（§2.1）：**三维风控矩阵** —— 地域与网络（Supported Regions / 机房 IP / 地区跳变）、
> 行为指纹（Canvas/WebGL 比对 / 防拼车）、API 调用异常（突发频次 / 爬虫节奏 / 降速降 Tier）。
>
> 第三轮补充（§2.2）：**凡是文案写「彻底移除（不可恢复）」的删除一律改软删除，供政府机关调查使用；
> 且前端/法务文案不改**（owner 决策 2026-10-10）。
>
> 第四轮补充（§2.3）：**被标记账户的人机验证默认走 trycap（Cap）或 Cloudflare Turnstile，
> 并支持在 `/admin/captcha-providers` 前后端可改** —— 结论是现有场景机制**做不到**，
> 必须新增 `step_up` 场景 + 每场景供应商白名单（RC-24）。
>
> 第五轮补充（§2.4）：**四层风控落地策略**（接入层 / 配额 / 合规门禁 / 内容与输出安全）——
> 零件基本都在，本轮做缺口加固与接线（RC-25～RC-35）；
> 其中 **WAF 必须豁免邮件系统 API**（`/api/email`、`/api/outemail`）是新增硬要求（RC-33）。
>
> 本文只做**只读审查 + 设计**，未改动任何生产代码，未运行构建/测试/lint（`AGENTS.md` §1 本地禁令）。
> 结论以本仓 HEAD `3fd20026`（2026-10-10 22:07 +0800）为基线。
> 编号 `RC-xx` 供后续修复批次逐条追溯（方法论 §一-8）。

## 0. 结论速览

| 需求 | 现状 | 判定 |
| --- | --- | --- |
| 封禁账户 | `accountStatus: suspended` + `disabled` 已实现，认证中间件拦得住 | **已具备**，但缺原因/证据/会话清理/统一出口（RC-07） |
| 危险账户「每操作弹人机验证」 | **完全没有账户级闸门**。人机验证只看「三家供应商有没有一家可用」，与账户无关 | **需新建**（RC-02 / RC-03），是本轮工作量主体 |
| 标记融入历来登录 IP risk score | 只有 `lastLoginIp` 单值；IP 风险分是 IP 维度、24h 缓存；**账户×IP 风险从未沉淀** | **需新建**（RC-04 / RC-06） |
| 删除一律软删除 | 用户删除是**物理删除 + 级联删除风控证据表**；TTS 历史已有软删除先例可抄 | **与需求直接冲突**（RC-01） |
| 注册滥用 | 邀请码 + 主流邮箱白名单 + 人机验证 + 邮件冷却已有；缺邮箱规范化、IP/指纹维度配额、注册风控入库 | **部分具备**（RC-05） |
| 地域与网络限制 | `supported-regions` **只是政策文本**，无技术强制；机房 IP 被显式排除在挑战判据外；跨地域跳变只用于移动端令牌 | **需新建**（RC-13～15） |
| 行为指纹 / 防拼车 | Canvas/WebGL 已在采集但只上行一个复合哈希；设备/会话台账齐全但**无阈值、无统计、无处置** | **需新建**（RC-16～17） |
| API 调用异常 | 只有固定每分钟额度 + 429 指标；Key 只有开/关两态，无降级档 | **需新建**（RC-18～20） |
| 删除语义统一 | 前端 61 处文案承诺「彻底移除 / 不可恢复」，对应后端绝大多数是**物理删除** | **需改造**（RC-21～22）；文案按 owner 要求**不改**（RC-23） |
| 逐步验证走哪家供应商 | 场景枚举只有 3 个，且场景**只能调权重、不能排除供应商**；权重 0 ≠ 排除 | **需新建**（RC-24：新增 `step_up` 场景 + 白名单，默认 trycap / Turnstile） |
| 四层风控落地（第五轮） | 接入层/配额/合规/输出安全四层各自已有零件，但存在缺口且**邮件 API 未豁免 WAF** | **需加固**（RC-25～35） |

一句话：**本仓风控的"零件"很全（IP 封禁 / proxycheck / IPQS / 设备指纹 / 设备风控策略 / 安全分 / 审计），
但"账户"这一层是空的** —— 没有一个字段表示「这个用户被盯上了」，也没有任何一处强制按账户风险升级验证。
本轮的正题是把账户风险这一层接上去，而不是再添一套 IP 风控。

## 2. 缺口清单（RC 编号）

> 字段：编号 / 位置 / 类型 / 详细（症状·根因·触发）/ 建议改法。
> 严重度：**P0** = 与需求直接冲突或安全底线；**P1** = 需求主体；**P2** = 配套加固。

### RC-01（P0）用户删除是物理删除，且级联抹掉风控证据

- 位置：`src/services/userService.ts:440`（`deleteUser`）、`:445-478`（cascade 清单）、`:494`（`UserModel.deleteOne`）
- 触发：管理员删号（`adminController.ts:890` 单人删、`:1032` 批量 `DELETE_USER`），以及注册失败回滚（`registrationHandlers.ts:259`、`verificationService.ts:162`）
- 现状：`session.withTransaction` 内对 **29 个集合** `deleteMany` 后物理删除用户文档。其中包含
  `device_trackings`、`security_events`、`auth_sessions`、`registration_invites`（用户侧）、
  `linuxdo_credit_orders`、`api_key_billing_events`、`translation_logs` 等。
  **只有 `audit_logs` 被刻意排除**（G2-30 注释）。
- 后果：删号即"洗白"——同一人换邮箱/邀请码即可重来，因为**设备、行为、IP、信用、邀请码使用链路全部消失**。
  这正是需求 (d) 要禁止的。
- 建议改法：
  1. 新增 `deletedAt`（时间戳）+ `accountStatus: "deleted"`（扩枚举），`deleteUser` 改为**软删除**：
     写 `deletedAt`、清 `password/passwordHash/password*/totpSecret/backupCodes/passkeys` 等凭据、
     `tokenVersion: $inc`、用户名/邮箱按需改成 `deleted_<id>` 释放唯一索引；**不删文档**。
  2. 级联清单拆成三类：
     - **保留并标记**（风控证据）：`device_trackings`、`security_events`、`auth_sessions`（改 `revokedAt`）、
       `api_key_billing_events`、`translation_logs`、`registration_invites`、`cdks`、`audit_logs`；
     - **真正删除**（用户内容/隐私）：`api_keys`、`access_tokens`、`oauth_*`、`account_identities`、
       `workspaces`、`voice_projects`、`tickets`、`user_preferences`、`short_urls` 等；
     - **保留但脱敏**：`bilibili_*`、`nexai_sync*`、`collaboration_sessions`。
  3. 保留项统一加 `subjectDeletedAt` 或在文档上留 `userId` 反查（现有索引已够：`security_events.userId`、
     `device_trackings.userId`）。
  4. **鉴权侧必须同步**：`authenticateToken.ts`、`auth.ts` 的 `authMiddlewareV2`、`wsAuthentication`
     需把 `deletedAt` 存在视为"不可登录"，否则软删除会变成"删了还能登"。
  5. 去重判定（`getUserByUsername/getUserByEmail`）要显式排除已软删除记录，
     或依赖改名后的 `deleted_<id>` 占位（推荐后者，语义更清楚）。
  6. **文案保持不变**（owner 于 2026-10-10 明确要求，见 RC-23）：
     `PrivacyConsentPanel.tsx:37`、`src/config/policyDocument.ts`、`src/templates/emailTemplates.ts`
     一律**不改**；因此实现侧必须保证「用户侧可见结果」与现有文案尽可能一致
     （用户列表里看不到、且不可自行恢复），差异只体现在数据库留存与管理员可见性上。

### RC-02（P0）没有"账户级人机验证闸门"，弹窗与后端鉴别都无从挂载

- 位置：`src/services/turnstile/providers.ts:486` `getCaptchaRequestPolicy()`、
  `src/controllers/auth/_state.ts:112` `verifyRequiredCaptcha()`
- 现状：判据是 `providers.filter(row => row.effective).length > 0` ——
  **"有没有供应商"决定"要不要验"，与请求方是谁、账户什么状态完全无关**。
  换句话说：一个已被确认刷量的账户，只要它按表单提交 captcha，待遇和正常用户一模一样。
- 后果：需求 (b) 的核心（危险账户每次操作都要验证）在代码里**没有任何落点**。
- 建议改法：
  1. 引入**账户风险档** `riskTier: normal | watch | restricted | danger | banned`（详见 §3）。
  2. 新增闸门服务 `accountStepUpService`，输入 `(req, user, riskTier)`，输出
     `{ required: boolean; scope: 'none'|'sensitive'|'all-writes'|'all'; challengeId?: string }`。
  3. `verifyRequiredCaptcha` 保持现在的表单级语义不变（**不要改它**，全站 7 处调用都在依赖它），
     在它**之外**加一层 `stepUpGuard` 中间件（§4.4）。
  4. 风险档必须可从运行时可配（`runtimeConfigService`），否则每次调整阈值都要发版。

### RC-03（P0）现有令牌模型撑不起"每次操作验一次"

- 位置：`ipVerificationService.issueToken`（`:283`）/ `verifyRequestToken`（`:764`）、
  `ipVerificationTokenModel.ts`、`runtimeConfigDefaults.ts:389`
- 现状：首访令牌绑定 `(fingerprint, ipAddress)`，TTL 40 分钟，`verifyRequestToken` **只校验存在与未过期**，
  同一张令牌在 40 分钟内可无限次复用；captchaToken 本身是一次性的，但只用在下发挑战那一刻。
- 后果：即便把"危险账户"接到首访闸门上，一次验证也能换来 40 分钟的免验证 —— 与"每一次操作都验证"相反。
- 建议改法：新建**单次挑战令牌** `step_up_challenges`（见 §4.3），与首访令牌并存、互不替代：
  - 字段：`challengeId`（随机）、`userId`、`riskTier`（签发时快照）、`routeKey`（方法+路由模板）、
    `payloadHash`（body 摘要，防"验一次、改内容重放"）、`issuedAt`、`expiresAt`（建议 120 秒）、
    `consumedAt`（原子单次消费）、`provider`、`ipAddress`、`fingerprint`。
  - 消费用 `findOneAndUpdate({ challengeId, consumedAt: null, expiresAt: { $gt: now } }, { $set: { consumedAt } })`，
    **原子单次**，并发重放只有一个成功。
  - 建 TTL 索引 `expiresAt` 自动清理，与 `ipBanModel` 同口径。

### RC-04（P1）账户数据模型没有任何风险字段

- 位置：`userService.ts:22-95`（schema）、`userStorageTypes.ts`
- 现状：与风控最接近的只有 `accountStatus(active|suspended)`；`role` 里的 `"trusted"` 只用于管理端筛选与
  OAuth 页面文案（`adminUserListHelpers.ts:43/324`、`OAuthAuthorizePage.tsx:83`），**不参与任何授权判定**。
  没有 `riskTier`、`riskScore`、`riskFlags`、`riskUpdatedAt`、`flaggedBy`、`stepUpUntil`、`deletedAt`。
- 后果：无法表达"观察中 / 受限 / 危险 / 需每次验证"这几种中间态；只有"正常"和"封停"两档。
- 建议改法（字段落在 `user_datas`，只加不删，全部带默认值，避免存量文档读不到）：
  ```
  riskTier: "normal"|"watch"|"restricted"|"danger"    // 默认 normal
  riskScore: Number          // 0-100，越高越危险（与 accountSecuritySummary 的"越高越安全"相反，命名要区分）
  riskFlags: [String]        // 如 HIGH_RISK_LOGIN_IP / MULTI_ACCOUNT_IP / DISPOSABLE_EMAIL
  riskUpdatedAt: Number
  flaggedBy: String          // "auto" | 管理员 id
  flagReason: String
  stepUpUntil: Number        // 0 = 不强制；>now = 该时刻前每次操作都要验
  stepUpMode: "sensitive"|"all-writes"|"all"
  deletedAt: Number          // 0/缺省 = 未删除（RC-01）
  ```
  `PUBLIC_USER_SELECT` / `PUBLIC_USER_SAFE_SELECT` / `ADMIN_USER_LIST_PROJECT`（`userService.ts:102/106/114`）
  要同步决定哪些字段出管理端、哪些**绝不出**用户自助接口（`stepUpUntil` 建议出，`riskFlags` 建议只出管理端，
  但前端需要知道"要不要弹窗"，所以**另设一个只读字段**给前端，见 RC-08）。

### RC-05（P1）注册反滥用缺"人/设备/IP"三个维度

- 位置：`registrationHandlers.ts:33-120`、`userRepository.ts:22` `buildNewUser`、`registrationInviteModel.ts`
- 现状（已有）：`fingerprint` 必填且 ≤512、四份政策逐项勾选、人机验证、主流邮箱白名单、
  `reserveAuthEmail` 冷却、验证码 5 次上限、邀请码校验 + 消费回滚。
- 缺口：
  1. **邮箱不做规范化**：`buildNewUser` 原样存 `email`（`userRepository.ts:22-34`），
     `getUserByEmail` 走精确匹配 ⇒ `User@Gmail.com` / `user+1@gmail.com` / `u.s.e.r@gmail.com`
     可各注册一个。这是最廉价的批量注册途径。
  2. **没有 IP / 指纹 / 设备维度的注册计数**：同一 IP 或同一指纹在 N 小时内注册 K 个账户没有闸门，
     也没有把注册时的 `ipAddress` / `fingerprint` / IP 风险分写进任何表。
  3. **邀请码使用记录不含来源**：`RegistrationInviteUse`（`registrationInviteModel.ts:4-11`）只有
     `userId/username/email/usedAt`，没有 IP/指纹 ⇒ 一个邀请码裂变成多号时看不出规律。
  4. 注册成功后**没有给新账户打初始风险档**（默认 normal），错失了"注册即评估"的窗口。
- 建议改法：
  1. 邮箱规范化：`trim().toLowerCase()`，并维护 gmail 点号/`+tag` 的归一化键（`emailCanonical`）
     用于**反滥用计数**，不改变用户可见邮箱；
     注册查重同时比 `email` 与 `emailCanonical`（后续同 `authEmailCooldownService` 口径）。
  2. 新增 `registration_attempts`（或复用 `security_events`）：记 `ipAddress`、`fingerprint`、
     `emailCanonical`、`inviteCode`、`outcome`、`ipRiskScore`；TTL 90-180 天。
  3. 闸门：同 IP 24h 内成功注册 > N、同指纹 > M、同 `emailCanonical` 前缀变体 > K 时，
     拒绝或降级为「人工审核 / 必须邀请码」。
  4. 邀请码消费时把 `ipAddress` / `fingerprint` 一起写进 `usedBy`。
  5. 注册成功即调一次 `evaluateAccountRisk`（§4.2），把初始 `riskTier` / `riskScore` 落库。

### RC-06（P1）历来登录 IP 的 risk score 从未沉淀到账户

- 位置：`authSessionModel.ts`（有 `ipAddress` + `ipLocation`，但**无风险分**）、
  `userService.ts:82`（只有 `lastLoginIp`/`lastLoginAt` 单值）、
  `proxycheckRiskCacheModel.ts`（IP 维度、TTL 24h）
- 现状：IP 风险分是**IP 维度**的临时结论，24h 后过期；账户维度只剩"最后一次登录 IP"这一格。
  需求 (c) 要求的"历来登录 IP risk score"**没有数据载体**。
- 建议改法：
  1. 新增 `account_ip_signals`（账户 × IP 事实表）：
     `userId`、`ipAddress`、`ipLocation`、`firstSeenAt`、`lastSeenAt`、`loginCount`、
     `riskScore`、`riskLevel`、`flags`、`source`（proxycheck/ipqs）、`riskCheckedAt`。
     唯一索引 `(userId, ipAddress)`；查询索引 `(userId, lastSeenAt: -1)`。
  2. 写入点：登录成功（`loginHandlers.ts:319`、`totpController.ts:465`、`passkeyHandlers.ts:122`、
     `googleAuthService.ts:271`）统一调 `recordAccountIpSignal(userId, ip, sessionMeta)`，

### RC-08（P1）前端没有"逐步验证弹窗"的编排层

- 位置：`frontend/src/components/ManagedCaptcha.tsx`（页面内嵌控件）、

- 后果：需求 (b) 的前端一半（"每一次操作都弹窗")没有承载物。
- 建议改法：
  1. 新增全局 `StepUpGateProvider`（挂在 `App.tsx` 的 Provider 层）+ `useStepUp()`；

  4. 用户取消/超时要有明确出口（返回原错误 + 提示），不能静默吞掉。

### RC-09（P1）"每一次操作"的定义缺失，直接实现会打死应用

- 位置：全站中间件顺序（`src/app/assembly.ts`）

- 风险：若字面执行"后端每一次操作都鉴别"，则 `GET /api/user/me`、`GET /api/tts/history`、

#### RC-17（P1）没有「拼车 / 共享账号」检测，也没有对应处置

- 位置：`src/models/deviceTrackingModel.ts:54`（唯一索引 `(userId, deviceFingerprint)`，已有「一账户多设备」计数基础）、
  `src/models/authSessionModel.ts:39`（`(userId, deviceKey, lastActivityAt)` 索引）、
  `src/services/authSessionService.ts:264`（`revokeAllAuthSessions`，现成的处置手段）

  但**没有任何阈值、没有定时统计、没有任何自动处置**。管理端也没有相应按钮。
- 后果：需求「防拼车（多设备、多 IP 短期高并发）→ 共享账号一网打尽」无落点。
- 建议改法：
  1. 新增 `account_access_signals`（或直接由 `account_ip_signals` + `device_trackings` + `auth_sessions` 聚合）：
     统计窗口内 `distinctDeviceCount` / `distinctIpCount` / `distinctCountryCount` /
     **`concurrentSessionCount`** / `requestsPerMinute`。

     `distinctDeviceCount ≥ N` **且** `distinctCountryCount ≥ 2` **且** `concurrentSessionCount ≥ M`
     → `riskFlags: ACCOUNT_SHARING_SUSPECTED`，按配置升 `restricted`（先验证）或 `danger`（直接处置）。
  3. 处置（对应需求「全员封禁/一网打尽」）：`danger` 档执行 `revokeAllAuthSessions(userId)`
     —— 所有设备一起下线 —— 并强制全员 step-up；连续命中则升级为 `banned`。
  4. **必须给合法多设备场景留白**：`role` 枚举里已存在但从未参与判定的 `"trusted"`
     （`userStorageTypes.ts:18`；仅被管理端筛选与 OAuth 页面文案引用，
     `adminUserListHelpers.ts:43/324`、`OAuthAuthorizePage.tsx:83`）正好可以启用为
     「经管理员确认的多设备账户」豁免标记，否则会误伤真实多端用户（手机+平板+两台电脑是常态）。
  5. **反例防护**：企业/校园 NAT 会让大量无关用户共享出口 IP，因此 IP 维度只能做**加权**、
     不能单独判定 —— 与 §4.6 已有原则一致。
  6. 隐私：设备清单一类聚合结果只在管理端可见；用户侧最多展示「当前活跃设备」。

- 后果：需求「突发异常高频请求、规律性爬虫节奏」没有检测手段。
- 建议改法：
  1. 新增 `api_usage_windows`（`keyId`/`userId` × 分钟桶）：记 `count`、`endpointHistogram`、
     `interArrivalMean` / `interArrivalVariance`（滑动计算，不存原始时间戳数组）。
  2. 两条判据：
     - **突增**：`currentWindow / p95(last7d windows)` 超阈值 → `SPIKE`；
     - **节奏**：`cv = σ/μ < 0.15` 且样本数 ≥ 30 → `ROBOTIC_CADENCE`
       （人工操作间隔方差大，脚本轮询/爬取间隔极规整，这是低成本高信噪比判据）。
  3. 先跑观察期（结果只进 `api_usage_windows` 与 `security_events`），
     阈值稳定后再接自动处置 —— 对齐 `nexaiSecurityService` 的 `MONITOR` 档设计思路。

#### RC-19（P1）API Key 只有开/关两态，没有「降速 / 降 Tier / 临时封禁」载体

- 位置：`src/models/apiKeyModel.ts:36`（只有 `enabled: boolean`，无等级概念）、
  `src/services/apiKeyService.ts:279`（`revokeKey` 就是 `enabled: false`）、
  `src/middleware/apiKeyAuth.ts:85`（429 一次性拒绝，无持续降级）
- 现状：需求里的「降速（Rate Limit）、临时封禁或注销 Tier 权限」没有载体 —— 要么全开要么全关，
  而「立即吊销」是唯一可用的重手段。
- 建议改法：
  1. `ApiKeyDoc` 扩展：`status: "active"|"throttled"|"suspended"`、`penaltyUntil: Date|null`、
     `effectiveRateLimit?: number`（缺省时回落到 `rateLimit`）。
  2. `apiKeyAuth` 按 `status` 分派：`active` 原额度；`throttled` 额度打到 10% 并带 `Retry-After`；
     `suspended` 回 `403 { code: "API_KEY_SUSPENDED" }`（**必须带 code**，否则前端/客户端识别不了）。
  3. 新管理员动作 `API_KEY_REVOKE`（需求原文「API Key 立即吊销」）走 RC-07 的统一出口 + 审计。
  4. `danger` 档账户的**全部** Key 由 `accountRiskService` 统一置 `suspended`，而不是逐个手工处理。
  5. 归因：吊销/降速必须写 `reason` 与 `source`（`auto:SPIKE` / `auto:ROBOTIC_CADENCE` / `manual:<operatorId>`），
     否则用户来申诉时无法解释。

#### RC-20（P2）违规拦截计数只在 IP 维度，未按账户聚合

- 位置：`src/services/turnstile/ipBan.ts`（`violationCount` 是 IP 维度）、`src/models/ipBanModel.ts:9`、
  账户维度只有工单的 `ticketViolationCount`（`userService.ts:85`）
- 现状：需求「高频触发违规拦截」作为**账户**滥用特征时不可见 —— 同一个账户换 IP 继续违规，计数就重置。
- 建议改法：违规拦截时同时写 `security_events` 的 `ACCOUNT_ABUSE_*` 事件，
  由 §4.2 的 `evaluateAccountRisk` 聚合进 `riskScore`；账户侧阈值独立于 IP 侧阈值。

### RC-22（P0）取证保留与调查调取链路（“给政府机关调查使用”的落地）

软删除只解决“数据还在”，不解决“能安全、可追溯地交出去”。本项是**本任务真正的交付物**。

1. **保留期**：软删除记录**不设 TTL**（与 `audit_logs` 60 天口径不同，参考 `policyDocument.ts:385`）。
   必须显式写明保留期与依据，不能“默认永久”而没有依据。
2. **TTL 集合无法被软删除拦住**（**最容易漏的坑**）：
   `ipBanModel.ts:31`、`accessTokenModel`、`ipVerificationTokenModel`、
   `verificationTokenModel`、`proxycheckRiskCacheModel`、`authEmailCooldownModel` 等
   都建了 Mongo TTL 索引。**TTL 在数据库内部删除，不受应用层 `subjectDeletedAt` 控制**。
   方案（二选一，需 owner 定，见 D8）：
   - (a) 去掉 TTL，改由应用层定时任务清理，清理前先查 `legal_holds`；
   - (b) 保留 TTL，但在命中 `legal_holds` 时把文档**搬移**到不受 TTL 约束的保留集（如 `forensic_archives`）。
   推荐 (a)：逻辑单一，符合“不再有东西绕过保留判定”的目标。
3. **法律保留 hold**：新增 `legal_holds`（`scope: user|fingerprint|ip`、`value`、`caseRef`、
   `issuedBy`、`issuedAt`、`expiresAt`、`reason`）。命中 hold 的对象**禁止任何物理删除**
   （含 TTL 与管理员硬删）；`softDeleteService`、`deleteUser`、所有清理任务都要先查 hold。
4. **访问控制**：软删除数据默认对**所有管理员隐藏**；只在 `superadmin` + 专页（待登记到
   `src/config/adminPages.ts`，参照 `ip-ban` / `ip-risk-logs` 的登记方式）可见。
   普通 `admin` 看得到“有记录被删除”，看不到内容 —— 与现有 adminScope 分档一致。
5. **取证导出**：新增 `POST /api/admin/forensic/export`，按 `userId` / `ip` / `fingerprint` / 时间窗
   导出，产出带 SHA-256 校验和的归档（参照 `policyConsentService` 的 checksum 思路，
   但需覆盖**多集合**并固定字段顺序）。导出本身也是一次受审计事件。
6. **审计每一位访问者**：查看 / 导出 / 恢复软删除数据，一律写 `audit_logs` **与** `security_events`
   （谁、何时、什么范围、什么理由）。现有 `audit_logs` 只有 60 天（`policyDocument.ts:385`），
   而调查周期可能更长 ⇒ 取证访问的审计最好入**独立、不设 TTL**的集合。
7. **加密与最小化**：软删除区存储加密（复用现有 AES-256-GCM + HKDF 主密钥派生范式，
   参考 `mediaToolCookiesCrypto.ts`）；导出时按 hold 的 scope 限定最小必要字段。
8. **接口契约**：所有新增处罚/限制接口必须带稳定 `code`（`CLAUDE.md` 安全注意事项）。

## 2.3 逐步验证的供应商选择（第四轮需求）

> 需求：**被标记账户的人机验证一律默认走 trycap（Cap）或 Cloudflare Turnstile，
> 并支持在 `/admin/captcha-providers` 前后端可改。**

### RC-24（P0）现有场景机制**无法限制供应商**，必须新增 `step_up` 场景 + 供应商白名单

#### 现状与关键证据

| # | 事实 | 位置 |
| --- | --- | --- |
| 1 | 场景枚举写死 3 个：`default / first_visit / standalone`，没有“被标记账户”这一场景 | `src/services/turnstile/types.ts:92/94/96` |
| 2 | 场景只控制**权重**与**策略**，不控制**候选集合**：先按 `effective`（enabled + 凭据齐 + 配额未耗尽）过滤，再按 `effectiveScenarioWeights[scenario]` 出权重 | `providers.ts:238`、判定 `:275-276`、过滤 `:322`、candidates `:330-336` |
| 3 | **权重 0 ≠ 排除**：`pickWeightedProvider` 在 `total <= 0` 时退化为**等概率抽取**；`failover` 只看 `priority`、`round_robin` 不看权重 | `allocation.ts:319`、回落分支 `:330-333` |
| 4 | 前端场景枚举也硬编码，且分布在四处 | `captcha-providers/types.ts:7`、场景清单 `:253-284`（`CAPTCHA_COVERAGE`）、草稿默认 `ProvidersTab.tsx:124`、`ManagedCaptcha.tsx:59` |
| 5 | **最容易漏的一处**：落库归一化只遍历写死的三个场景，新场景的配置会被**静默丢弃** | `src/services/turnstile/models.ts:202`（`normalizeStoredScenarioWeights`） |

**结论**：需求里的“**一律**走 trycap 或 Turnstile”**不能靠现有机制实现**。
把 hCaptcha 权重设为 0 依然可能被选中（事实 3），在 `failover` / `round_robin` 策略下权重根本不参与。
必须新增一个**每场景供应商白名单**，它是硬约束而不是概率。

#### 建议改法

1. **新增场景** `step_up`（标签「被标记账户逐步验证」）：
   - `CaptchaScenario` 扩为 4 个（`types.ts:92/94/96`），
   - `normalizeStoredScenarioWeights`（`models.ts:202`）改为遍历 `CAPTCHA_SCENARIOS` 常量
     —— **不再手写数组**，否则下次加场景会重踩同一个坑，
   - 前端 `types.ts:7/78/87`、`ProvidersTab.tsx:124`、`ManagedCaptcha.tsx:59` 同步。
2. **新增白名单字段**（落在 allocation policy 文档，与 `scenarioStrategies` 并列）：
   ```ts
   scenarioProviderAllowlist: Partial<Record<CaptchaScenario, CaptchaProviderId[]>>
   ```
   - `DEFAULT_ALLOCATION_POLICY`（`allocation.ts:95`）默认设为
     `{ step_up: ["trycap", "turnstile"] }` —— **正好是需求要求的默认组合**；
   - 归一化新增 `normalizeScenarioAllowlist()`，与 `normalizeScenarioStrategies()`（`:183`）同形：
     去重、剔除非法 provider、空数组视为“未设置”（否则一个空数组会把该场景变成无候选）。
3. **生效点**：`collectCaptchaProviders()`（`providers.ts:238`）在 `effectiveRows` 之后、
   构建 `candidates`（`:330`）之前，取 `scenario` 的白名单做**交集**；
   白名单未设置的场景行为**逐字节不变**（向后兼容）。
   同时 `providers` 快照新增 `allowedForScenario: boolean`，让管理端能显示“这家在本场景被排除”。
4. **前后端共用同一常量**：`step_up` 这个字符串必须来自**同一份定义**
   （后端 `CAPTCHA_SCENARIOS` → 前端通过 `secure-captcha-config` 或构建期生成物获取），
   不允许后端返回 `"step_up"`、前端写 `"stepUp"` 这类字面量分叉 —— 仓库已有同类教训
   （`CAPTCHA-08` 的字段名不一致，见 `docs/audit-2026-10-07-captcha-lifecycle.md`）。
5. **与逐步验证闸门联动**（RC-02/RC-03）：
   - 后端 `stepUpGuard` 返回 `403 { code: "STEP_UP_REQUIRED", scenario: "step_up" }`；
   - 前端 `StepUpGate` 用 `ManagedCaptcha scenario="step_up"`（而非现在的 `standalone`）；
   - 后端在 `POST /api/step-up/challenge` 校挑战时，**重新校验该账户当前是否仍需 step-up**，
     且校验场景仍为 `step_up`（防止前端传 `default` 拿到更宽松的供应商集）。
6. **白名单耗尽时：`fail_closed`（owner 已定 2026-10-10，D11）**，且**不引入 hCaptcha 后备**
   （owner 已定，D12）。具体行为必须写死成下面四条，否则“失败关闭”会变成“静默放行”或“用户被卡死却不知道为什么”：
   - 判定：`step_up` 场景的 `candidates` 交集为空（trycap/turnstile 都 `effective=false`）时，
     **不得**回落到全局 enabled 列表、不得回落 `default` 场景、不得签发任何绕过令牌；
   - 对**被标记账户**：写操作一律 `403 { code: "STEP_UP_UNAVAILABLE" }`（带 `supportEmail`，
     复用 `providerAuthErrors` 的契约形状），并降为只读；**绝不静默放行**；
   - 对**未被标记账户**：`default` / `first_visit` / `standalone` 场景**完全不受影响**
     （hCaptcha 仍照常在这些场景服务）—— 失败关闭只作用于 `step_up`，
     不能把全站可用性绑到 trycap/Turnstile 上；
   - **告警与逃生舱**：进入该分支时必须按 `logger.error` + 可告警信号输出（不是 warn），
     并在 `/admin/captcha-providers` 概览处显示“step_up 白名单已耗尽”的红字提示；
     恢复手段 = 管理员在面板修凭据/配额，或**有审计地**临时调整白名单（调整走既有 PUT 契约，
     自动进 `audit_logs`），不另做“一键绕过”后门。
7. **上线前置（硬条件）**：`trycap` 与 `turnstile` 必须**凭据齐**且配额未耗尽，
   否则 `effective=false`（`providers.ts:320-322`），白名单交集为空、直接落入第 6 条的 `fail_closed` 分支。
   自托管 Cap 需先确认 `readProviderCredentials("trycap")` 的 siteKey/secret/endpoint 已配。
   **`fail_closed` 的代价必须提前告知运维**：trycap/Turnstile 双挂时，被标记账户的写操作会全停
   （读仍可用，未标记账户不受影响）—— 这是有意为之，不是故障；但必须告警，不能靠用户报障才发现。

## 2.4 四层风控落地策略（第五轮需求）

> （一）接入层网络与设备防刷、（二）核心资产与消费配额风控、

### 第一层：接入层网络与设备防刷

#### RC-25（P1）真实 IP 强校验：解析链已存在，但需要加固与部署前提固定

- 位置：`src/utils/trustProxy.ts`（`parseTrustProxySetting`）、`src/app/assembly.ts:240`（`app.set("trust proxy", ...)`）、
  `src/utils/ipUtils.ts:25-45`（`extractRealIP`：优先 `req.ip`，否则回退头部）、
  `src/app/assembly.ts:125`（注释已声明“只取 TCP 层地址”）
- 现状：代理跳数解析、`req.ip` 优先、头部回退路径都已存在。
- **残留风险**：`extractRealIP` 在拿不到 `req.ip` 时**会回退到可伪造的头部**（`ipUtils.ts:38` 自己的注释就写着
  “在未走 CF 的部署或 trust proxy 配置使 req.ip 失效时可被伪造，影响封禁/限流/用量统计”）。
  一旦回退发生，`ipBanCheck` / 限流 / 用量统计全部建立在可伪造的地址上 —— 伪造 `X-Forwarded-For`
  即可给他人“刷出”封禁，或把自己伪装成干净 IP 绕过封禁。
- 建议改法：
  1. `TRUST_PROXY` 必填化：生产环境未配置时**启动直接抛错**（rather than 静默回退）。
  2. 回退分支收紧：只有从**可信代理**（TCP 对端命中 `TRUST_PROXY` 声明的网段/跳数）来的请求才允许读头部；
     否则**不回退**，直接用 TCP 地址（宁可将 NAT 后的多人归为一个 IP，也不接受一个可伪造的值）。
  3. `ipBanCheck` 的 CIDR 匹配与 Redis 同步黑名单保持现有语义，但封禁写入口要统一到 RC-07 的出口并记下“判据是哪个地址”。

#### RC-26（P1）IP 风险需从“两档”扩为“三档 + 硬切断”，并把 WebRTC 异常接上

- 位置：`src/services/ipRiskService.ts:113`（`buildIpRiskDecision`）、
  `src/config/runtimeConfigDefaults.ts:503-504`（`challengeRiskScore=66` / `blockRiskScore=90`）、
  `src/security/ipBlockPage.ts`（现有封禁/风险拦截页面）、
  `src/models/proxycheckProbeReportModel.ts`（WebRTC/出口 IP 探测落库）
- 现状：只有「挑战 / 封禁」两档，且**封禁仅由首访闸门产出**（`caller === "first_visit_gate"`）；
  普通 API 调用路径只 `report`，不拦截。
- 缺口：
  1. “中风险→人机验证”已实现（challenge），但**只作用于首访**；已登录用户的中风险出口不再复查。
  2. “高风险→切断连接 + 渲染拦截页”目前只在首访且仅在写库成功时发生；
     `manualBanIp` 失败时降级为挑战（合理），但没有告警。
  3. **WebRTC 泄露异常完全未接入**：探测数据只在表里，无任何闸门消费。
- 建议改法：
  1. 三档定义与 §3 的风险档对齐：低→放行；中（机房/VPN/高风险出口）→ `ManagedCaptcha` 或 PoW 挑战；
     高→写 `IpBanModel` + 渲染拦截页。
  2. 将 `shouldBlock` 从“仅首访闸门”扩展到**已登录请求的中阶复查**（按账户风险档控制频率，避免每请求外查）。
  3. WebRTC 异常（`proxycheckProbeReportModel` 的 mismatch/可比性判据）接入 `account_ip_signals`（RC-06），
     作为账户风险分的一路信号，而不是直接封禁 —— 探测报告是**客户端上报**，单独作为封禁判据就是新攻击面
     （与 `nexaiSecurityService.ts:162` 的既有原则一致）。

#### RC-27（P1）昂贵端点限流：矩阵已有，缺的是“双键 + 并发”约束

- 位置：`src/middleware/routeLimiters.ts`（64 个定义，`ttsGenerate` / `transcribe` / `authLogin` / `authRegister` / `cdict*`）、
  `src/services/sharedRateLimitStore.ts`（Redis / 内存档）
- 现状：路由级限流**已存在**，但主要是单键（按 IP 或按用户）与固定窗口/令牌桶。
- 缺口（按需求逐项核对）：
  1. `/api/tts/generate` 与 `/api/transcribe`：需要**`User ID + IP` 双键**与**突发并发上限**，
     否则同一账号换 IP 即可并行刷算力；而纯按 IP 会把 NAT 后的正常用户算作滥用。
  2. `/api/auth/*`：已有 `loginAttempts` 锁定（`_state.ts` 的 15 分钟锁）+ 限流，
     但**没有指数退避**；且 `loginAttempts` 是**进程内存 Map**，多实例下不同步（单实例无影响，扩容后就漏）。
  3. `/api/cdict/donate/claim`：需确认其专属频次（需求写“每 IP 每小时 10 次”）。
     现有 `cdict*` 系列限流器（`cdictIngress`/`cdict`/`cdictTrusted`…）是按“信任等级 + 安装 ID”分桶的，
     **需要一个面向 claim 的专用桶**（不与翻译类请求共用）。
- 建议改法：把这三个点写成**声明式限流定义**（复用 `limiterFromDefinition`），双键用 `keyGenerator` 组合
  `userId + ip`；并发用已有的后台任务注册表（`backgroundTaskRegistry`）计数并拒绝超限；
  指数退避与锁定状态**存 Redis（有则用）/ Mongo（无 Redis 时）**，不再只靠进程 Map。

### 第四层：内容过滤与输出安全

#### RC-33（P0）输入侧 WAF：**必须豁免邮件系统 API**（本轮新增的硬要求）

- 位置：`src/security/securityPolicy.ts:65-70`（`securityBypassPolicy.waf`，当前只有 4 条：
  `/api/auth/login`、`/api/auth/register`、`/api/ecoenchants/v1/webhooks`、`/api/data-collection`）、
  `src/middleware/wafMiddleware.ts:86`（`isWafBypassPath`）、
  `src/routes/routeModules/earlyModules.ts:83-100`（`email-routes` → `/api/email`、`outemail-routes` → `/api/outemail`）
- 现状（**明确结论**）：**邮件系统的 API 目前没有 WAF 豁免** —— 
  `securityBypassPolicy.waf` 的 4 条里不含 `/api/email` 与 `/api/outemail`。
- 风险：邮件系统天然携带**HTML 正文**（`templates/emailTemplates.ts` 全是 HTML 模板）与**外来回调/退订参数**。
  WAF 的请求体扫描（`wafMiddleware.ts:194-232` 的 `BODY_FIELD_WHITELIST` / `WHITELIST_PREFIX_SET` 白名单子树）
  对邮件 HTML 很容易误报：一旦被拦住，**发送失败、退订失效、退信回调丢失**，
  而这类故障往往表现为“邮件系统偶发不工作”，极难归因。
- 建议改法：
  1. 在 `securityBypassPolicy.waf` 增加：
     - `{ match: "prefix", value: "/api/email", note: "Email HTML bodies and provider callbacks are not WAF-scannable" }`
     - `{ match: "prefix", value: "/api/outemail", note: "Same as /api/email" }`
  2. **豁免不得敞开注入面**：邮件路径必须靠**其它已有约束**补位，而不是“啥都不管”——
     `/api/email` 的写操作已是 superadmin 级 + 路由级限流，
     `/api/outemail` 的 send 走 API Key/code 鉴权 + 专属限流（`earlyModules.ts:96`）。
     实现前逐个确认这两条仍然成立。
  3. 邮件模板渲染侧不要把用户输入拼进 HTML（若已有插值，走 `escapeHtml`）；
     WAF 豁免的是**扫描**，不是**输出编码**，两者不能相互替代。
  4. 同时入 `securityBypassPolicy` 的**一致性校验**通道：`securityPolicy.ts:54` 注释提到
     `security-bypass-inconsistency` 会告警（不是启动失败）——新增豁免后必须确认不报该告警，
     否则可能是“静态规则与路由模块声明不一致”，会让豁免静默失效。

#### RC-34（P2）输出侧：DOMPurify 已基本覆盖，剩两处需逐个核实

- 位置：`frontend/src/utils/integrityCheck.ts`（6 处 `innerHTML`赋值：`:960/1341/1541/1611/2438`、
  读取处 `:940/1396/2222/2239/2586`）、`frontend/src/components/EmailSender.tsx:1135/1525`

- 现状：公告/制品/广播/大小写工具都已过 `DOMPurify`（见上面的“事实校正”表）；
  `src/utils/announcementHtml.ts` 连**服务端**渲染也过了同一个库，口径是对的。
- 待核实（**不预设结论**）：
  1. `integrityCheck.ts` 的 6 处 `innerHTML` 是模板字符串拼接。若插值全部来自常量与内部 ID，则无风险；
     只要有一处掺入外部/存储值，就是存储型 XSS。逐个看插值来源。
  2. `EmailSender.tsx` 的邮件预览：若渲染的是管理员自编 HTML（预期行为）、且在**同源**下直接注入，
     则为管理员侧 XSS 面（一旦某个低权限入口能影响预览内容，就会升级）。

- 现状：需求描述的全部要点**已实现** —— 敏感字段（验证码/Token/密码）脱敏后入库、
  统一批量落库并有落盘兜底、默认 60 天 TTL（与 `policyDocument.ts:385` 的政策口径一致）。
- 缺口 / 冲突：
  1. 本轮新增的全部敏感动作（风险档升降、step-up 开关、取证导出、软删除、

## 3. 建议的账户风险分档与动作矩阵

`riskTier`（账户唯一档位，取值单调升级、可人工降级）：

| 档位 | 含义 | 触发（示例） | 强制动作 |
| --- | --- | --- | --- |
| `normal` | 正常 | 默认 | 现有表单级人机验证 + 首访闸门 |
| `watch` | 观察 | 新号 7 天内 / 近期登录 IP 风险分 60-79 / 单设备多账号 | 登录必验；风险分持续采样；管理端可见标记 |
| `restricted` | 受限 | 风险分 ≥ 80 / 命中 ≥2 个 flag / 多次 `RISK_BLOCKED` | `sensitive` 档每次操作验人机 + 限流额度减半 + 禁用高风险功能（导出/API Key/图床） |
| `danger` | 危险 | 风险分 ≥ 90 / 确认多开或自动化 / 管理员手工标记 | `all-writes`（可升 `all`）每次操作验人机 + 只读降级 + 存量会话强制重验 |
| `banned` | 封禁 | 管理员封停 / 严重违规 | 403 `ACCOUNT_SUSPENDED`（现有行为），不再给验证机会 |

**升降级规则**：自动升级只做 `normal → watch → restricted`，**`danger` / `banned` 必须人工确认或
由管理员开启的自动规则触发**（避免误封真实用户）；降级需要"观察窗口内无新命中"或管理员手动。

**`stepUpUntil`**：`restricted`/`danger` 档签名成一个到期时间，避免"永久每次验证"把用户卡死；
到期前若风险分仍高则续期。管理员也可给一个固定时段。

### 3.1 三维风控矩阵：规则 → 检测信号 → 现有落点 → 处置

| 维度 | 规则 | 检测信号（已有 / 需新增） | 现有落点 | 处置（按档位） |
| --- | --- | --- | --- | --- |
| **地域与网络** | 严格执行 Supported Regions | `ip.ts` 的 `country`/`region`；proxycheck `country`/`isocode`（已有） | 无（政策文本） | 注册拒绝 / 登录阻断 / API Key 吊销（RC-13） |
| 同上 | 机房数据中心 IP（ASN/IDC） | proxycheck `hosting`/`networkType`/`asn`、Scamalytics `is_datacenter`（已采集、无消费方） | 仅进 `risk` 分权重 | 注册拒绝（无邀请码时）；升档（RC-14） |
| 同上 | 瞬时跨地域跳变 | `auth_sessions.ipLocation`（已有）+ `isGeoJump()`（已有但仅移动端） | `mobileTokenRiskService` | 记录 + 提醒；`watch` 以上进 step-up（RC-15） |
| **行为指纹** | Canvas/WebGL 指纹比对 | `fingerprint.ts:110/129`（已采集，但只上行复合 hash） | `user_datas.fingerprints[]` | `FP_COMPONENT_DRIFT` / `FP_SHARED_ACROSS_ACCOUNTS` → 升档（RC-16） |
| 同上 | 防拼车（多设备/多 IP/短期高并发） | `device_trackings`、`auth_sessions`（数据已有，无阈值无统计） | 无 | 三条件联立 → `ACCOUNT_SHARING_SUSPECTED` → `revokeAllAuthSessions` + 全员 step-up（RC-17） |
| **API 调用异常** | 突发异常高频请求 | `apiKeyRateLimiter` 额度（已有）+ `RateLimitMetricsRegistry`（仅观测） | 固定额度 429 | `SPIKE` → 降速 / 临时封禁（RC-18/19） |
| 同上 | 规律性爬虫节奏 | 需新增：`interArrivalMean/Variance` | 无 | `ROBOTIC_CADENCE` → 降速 / 降 Tier |
| 同上 | 高频触发违规拦截 | IP 维度 `violationCount`（已有），账户维度缺失 | `ipBanModel` | 账户维 `ACCOUNT_ABUSE_*` → 进 `riskScore`（RC-20） |

**注**：表里的"处置"全部走 §3 的 `riskTier` 档位，**不新建第二套处罚体系**。
三维矩阵是**信号来源**，`riskTier` 是**唯一处罚状态机** —— 否则会出现"IP 说封、账户说放行"的自相矛盾。

## 4. 关键技术设计

### 4.1 数据模型（新增/扩展）

| 对象 | 类型 | 关键字段 | 索引/TTL |
| --- | --- | --- | --- |
| `user_datas`（扩展） | 扩展 | `riskTier/riskScore/riskFlags/flaggedBy/flagReason/stepUpUntil/stepUpMode/deletedAt` | 现有 |
| `account_ip_signals` | 新 | `userId, ipAddress, ipLocation, firstSeenAt, lastSeenAt, loginCount, riskScore, riskLevel, flags[], riskCheckedAt` | `(userId, ipAddress)` 唯一；`(userId, lastSeenAt:-1)` |
| `step_up_challenges` | 新 | `challengeId, userId, routeKey, payloadHash, provider, ipAddress, fingerprint, issuedAt, expiresAt, consumedAt` | `challengeId` 唯一；`expiresAt` TTL |
| `account_risk_events` | 新（或复用 `security_events`） | `userId, action, fromTier, toTier, riskScore, flags[], reason, operatorId, createdAt` | `(userId, createdAt:-1)` |

> `account_risk_events` 能复用 `security_events`（已有 `userId`/`eventType`/`eventData`/`riskScore`）
> 就复用，少一张表；**必须先补 RC-12 的复合索引**。

### 4.2 账户风险聚合 `evaluateAccountRisk(userId)`

- 输入：`account_ip_signals`（近 30 天）+ `device_trackings` + `security_events` + 账户姿态
  （MFA/指纹）+ 注册新鲜度。
- 输出：`{ riskScore: 0-100, riskTier, flags[], reasons[] }`。
- 调用时机：**登录成功后**（同步，用已有缓存，不外呼）、**每次风险事件上报后**（异步）、
  **管理员面板打开账户详情时**（实时）、**定时任务**（建议 6h 一轮，复用 `backgroundTaskRegistry`）。
- 幂等：写入 `riskUpdatedAt`，同分同档不重复写事件。
- 纯函数化：核心折算逻辑写成纯函数（输入事实 → 输出分档），便于 Jest 直测，不依赖 Mongo
  —— 仓库里 `mobileTokenRiskService.collectRotationRiskSignals` / `isGeoJump` 就是这个范式。

### 4.3 单次挑战令牌生命周期（RC-03）

```
前端                         后端
 │ 任意请求（带会话）           │
 ├────────────────────────────►│ stepUpGuard：账户档位需要验证？
 │                             │   否 → next()
 │◄── 403 { code:"STEP_UP_REQUIRED", challenge:{...}} ──┤
 │ 弹 ManagedCaptcha(standalone)                        │
 │ 解出 { token, provider }                             │
 ├── POST /api/step-up/challenge { routeKey, payloadHash, token, provider } ──►
 │                             │ 校验 captcha → 建 challenge（TTL 120s，单次）
 │◄── 200 { challengeId } ─────┤
 ├── 重放原请求 + X-Step-Up-Challenge: <id> ───────────►│
 │                             │ 原子消费（consumedAt:null → now）
 │                             │ 校验 routeKey + payloadHash 匹配
 │◄── 200/4xx 原结果 ──────────┤
```

**要点**：
- 令牌绑定 `userId + routeKey + payloadHash`，杜绝"验一次改内容重放"；
- `routeKey` 用**路由模板**（`req.route.path`）而非具体 URL，否则带 id 的路径永远对不上；
- 消费必须**先消费后转发**：`findOneAndUpdate` 原子置 `consumedAt`，
  失败即拒绝，避免 TOCTOU（仓库已有同类教训，见 `softDeleteRecord` 的 owner-in-filter 注释）；
- 挑战创建要限流（复用 `routeLimiters.createLimiter`），防止"无限弹窗"本身成为可用性攻击面。

### 4.4 后端中间件插入点

- 位置：`assembly.ts` 的 **API 路由相位**，在 `authenticateToken` **之后**、业务路由 **之前**。
- 顺序：`authenticateToken`（拿到 `req.user`）→ **`accountStepUpGuard`** → 业务。
- 豁免清单（必须显式，且进 `securityPolicy` 白名单机制，便于审计）：
  `OPTIONS`、`/api/health`、`/api/status`、`/api/auth/logout`、step-up 挑战端点自身、
  `/static/**`、WebSocket 升级、以及 `shouldBypassSecurityComponent()` 已登记的内部路径。
- 契约：
  - `403 { success:false, error:"需要完成人机验证", code:"STEP_UP_REQUIRED", scope, routeKey? }`
  - **必须带稳定 `code`**（`CLAUDE.md` 安全注意事项：处罚类不带 `code` 前端识别不了）。
- 鉴权解耦：`stepUpGuard` 只读 `req.user.riskTier`（登录时已随用户文档取出，无需额外查询），
  避免"每个请求再多一次 Mongo 查"。

### 4.5 前端编排（RC-08）

- 新增：`frontend/src/components/StepUpGate.tsx` + `frontend/src/utils/stepUpQueue.ts`。
- `api.ts` 拦截器（`:171` 附近）加一条分支识别 `code === "STEP_UP_REQUIRED"`，
  与现有 `IP_VERIFICATION_REQUIRED` **并列但不合并**（一个是 IP 级、一个是账户级，恢复动作不同）。
- 原生客户端/脚本：`403 { unsupported: "interactive" }` 时不做弹窗，直接降级只读并提示。
- 注意 `ManagedCaptcha` 的历史坑（`docs/audit-2026-10-07-captcha-lifecycle.md`）：
  一次性令牌复用、控件过期信号、并发单飞 —— 新组件必须复用那轮修好的模式
  （`reset(consumedToken)`、`subscribeCaptchaRecovery`），不要另写一套。

### 4.6 明确不行 / 明确不做

| 想法 | 判定 | 原因 |
| --- | --- | --- |
| 所有 GET 每请求验人机 | ❌ | 页面加载几十请求；轮询/SSE/WS 直接废掉；原生客户端弹不出窗 |
| 把首访令牌当 step-up 令牌复用 | ❌ | TTL 40min 可复用，语义相反（RC-03） |
| 在 `verifyRequiredCaptcha` 里塞账户判断 | ❌ | 全站 7 处表单共用，改语义会连带影响登录/注册/TTS/图床/抽奖/CDK |
| 自动重放 POST/PATCH | ❌ | `api.ts:190` 已确立"非幂等不自动重试"，step-up 重放要沿用 |
| 匿名上报头部直接升级为封禁 | ❌ | `nexaiSecurityService.ts:162` 已明确此为攻击面（客户端可自报头部） |
| 软删除连带保留密码哈希 | ❌ | 软删除必须清凭据；只保留"这个人存在过 + 风险事实" |
| 为配合软删除而改掉「不可恢复」类文案 | ❌ | owner 已决策不改（RC-11/RC-23）；差异改为内部文档承接 |
| 对带 Mongo TTL 索引的集合直接套 `subjectDeletedAt` | ❌ | TTL 在数据库内部删除，不受应用层控制 —— 必须先去 TTL 或搬移（RC-22.2） |
| `step_up` 白名单耗尽时回落 hCaptcha 或全局 enabled 列表 | ❌ | owner 已定（D11/D12）：`fail_closed`，`step_up` 候选集恒等于白名单 |
| `step_up` 失败关闭时连读请求一起拦 | ❌ | 被标记账户应降为**只读**；拦读会把“验证服务抖一下”放大成“用户什么都干不了” |

## 7. 验证方式（按 `AGENTS.md` / 方法论）

- **本地零构建**：所有验证交 CI（`Node verification` / 后端 Jest / 前端 Vitest / 镜像 / CodeQL）。
- 静态自查（允许）：改动文件的花括号平衡、`git diff` 逐份核查。
- 判据（方法论 §五-36）：`check-runs` 用 jq 自判布尔 + 两次快照一致，不用 `--exit-status`。
- 每批必须带的回归测试：
  - B1：软删除后 `getUserByUsername/Email` 行为、鉴权拒绝、级联"保留/删除/脱敏"三分法各自断言；
  - B2：`evaluateAccountRisk` 纯函数表驱动（各风险分档边界）、`account_ip_signals` 幂等 upsert；
  - B3：挑战令牌单次消费（并发只有一个成功）、`routeKey`/`payloadHash` 不匹配拒绝、过期拒绝、
    豁免路径放行、`STEP_UP_REQUIRED` 契约形状；
  - B4：邮箱变体（大小写 / gmail 点号 / `+tag`）查重、同 IP 配额触发；
  - B5：多请求并发只弹一个弹窗、非幂等请求不自动重放、取消/超时出口；
  - B7：`isGeoJump` 公共化后原单测不回归；指纹分量漂移/跨账户共用判定表驱动；
    拼车规则三条件联立（分别缺一时不触发）；`ROBOTIC_CADENCE` 的 `cv` 边界值；
    Key `throttled`/`suspended` 下的额度与 `code` 契约；
  - B3/RC-24：`step_up` 场景的白名单**恒等于**候选集（把 hCaptcha 打开且权重调到最高也不出现）；
    白名单为空/命中全不可用时走 `fail_closed` 而非回落；
    `default` / `first_visit` / `standalone` 三个场景的候选集与旧行为逐字段一致（回归）；
    新增场景的落库往返（存 → 读）不被 `normalizeStoredScenarioWeights` 丢弃；
  - B8：**裸 `deleteOne` 治理闸门**（受管集合上出现裸删必须 CI 报错）；
    软删除后用户侧不可见 / 管理员默认不可见 / superadmin 可见；`legal_holds` 命中时
    （含 TTL 集合）任何路径都删不掉；取证导出带校验和且写审计；`status | softDeleteService` 幂等重删。
