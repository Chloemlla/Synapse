# 风控加固分析：账户标记、逐步验证与软删除（2026-10-10）

> 任务来源：用户要求「对普通用户 + 注册滥用做多方位全角度风控加强」，包含
> (a) 封禁账户，(b) **被标记的危险账户在前端每一次操作都弹人机验证、后端每一次操作都鉴别**，
> (c) 账户标记融入**历来登录 IP risk score**，(d) 用户在前/后端 profile 页面删除的**一律软删除**，风控仍可读。
>
> 第二轮补充（§2.1）：**三维风控矩阵** —— 地域与网络（Supported Regions / 机房 IP / 地区跳变）、
> 行为指纹（Canvas/WebGL 比对 / 防拼车）、API 调用异常（突发频次 / 爬虫节奏 / 降速降 Tier）。
>
> 第三轮补充（§2.2）：**凡是文案写「彻底移除（不可恢复）」的删除一律改软删除，供政府机关调查使用；
> 且前端/法务文案不改**（owner 决策 2026-10-10）。
>
> 第四轮补充（§2.3）：**被标记账户的人机验证默认走 trycap（Cap）或 Cloudflare Turnstile，
> 并支持在 `/admin/captcha-providers` 前后端可改** —— 结论是现有场景机制**做不到**，
> 必须新增 `step_up` 场景 + 每场景供应商白名单（RC-24）。
>
> 第五轮补充（§2.4）：**四层风控落地策略**（接入层 / 配额 / 合规门禁 / 内容与输出安全）——
> 零件基本都在，本轮做缺口加固与接线（RC-25～RC-35）；
> 其中 **WAF 必须豁免邮件系统 API**（`/api/email`、`/api/outemail`）是新增硬要求（RC-33）。
>
> 第六轮补充（§2.5）：**成本封锁与零信任极限制约**（动态 PoW / 惩罚极限化 /
> 文件沙箱 / 安全会话 3～5 分钟 + IP-UA 绑定 / 蜜罐诱捕 / Tarpit）（RC-36～RC-43）。
> 其中 **两项必须先裁决**（“不告知不申诉”与仓库既定惩罚态契约冲突、“IP 跳变即全站踢出”
> 会大规模误伤移动端），见 §2.5 开头的两个裁决块。
>
> 第七轮补充（§2.10）：**把重心转移到“动态风控”、“服务端会话上下文”与“资产颗粒度”** ——
> 请求端动态证明（PoW / 动态验签）、设备与网络信誉阻断、业务级数据切片与流式下发、
> 行为速率限制与异常熔断（RC-54～RC-58）。四条均非从零开始，本轮做的是“接到账户/会话维度 + 每次调用重新花成本”。
>
> 另：**风控对超级管理员豁免**（owner 要求）是跨批次不变量，见 §3.2 / RC-44 ——
> 必须在 step-up 闸门（B3）开工前先落地，否则第一版就有锁死运维者的风险。
>
> 本文只做**只读审查 + 设计**，未改动任何生产代码，未运行构建/测试/lint（`AGENTS.md` §1 本地禁令）。
> 结论以本仓 HEAD `3fd20026`（2026-10-10 22:07 +0800）为基线。
> 编号 `RC-xx` 供后续修复批次逐条追溯（方法论 §一-8）。

| 危险账户「每操作弹人机验证」 | **完全没有账户级闸门**。人机验证只看「三家供应商有没有一家可用」，与账户无关 | **需新建**（RC-02 / RC-03），是本轮工作量主体 |

| 行为指纹 / 防拼车 | Canvas/WebGL 已在采集但只上行一个复合哈希；设备/会话台账齐全但**无阈值、无统计、无处置** | **需新建**（RC-16～17） |

| 删除语义统一 | 前端 61 处文案承诺「彻底移除 / 不可恢复」，对应后端绝大多数是**物理删除** | **需改造**（RC-21～22）；文案按 owner 要求**不改**（RC-23） |

| 四层风控落地（第五轮） | 接入层/配额/合规/输出安全四层各自已有零件，但存在缺口且**邮件 API 未豁免 WAF** | **需加固**（RC-25～35） |
| 成本封锁与零信任（第六轮） | 安全会话 **10 分钟 TTL 且不绑 IP/UA**；媒体任务无看门狗；无蜜罐；无 Tarpit | **需新建**（RC-36～43），且**四项与现有契约/可用性相冲**，见两处“⚠ 必须先裁决” |

一句话：**本仓风控的"零件"很全（IP 封禁 / proxycheck / IPQS / 设备指纹 / 设备风控策略 / 安全分 / 审计），
但"账户"这一层是空的** —— 没有一个字段表示「这个用户被盯上了」，也没有任何一处强制按账户风险升级验证。
本轮的正题是把账户风险这一层接上去，而不是再添一套 IP 风控。

### RC-01（P0）用户删除是物理删除，且级联抹掉风控证据

- 位置：`src/services/userService.ts:440`（`deleteUser`）、`:445-478`（cascade 清单）、`:494`（`UserModel.deleteOne`）
- 触发：管理员删号（`adminController.ts:890` 单人删、`:1032` 批量 `DELETE_USER`），以及注册失败回滚（`registrationHandlers.ts:259`、`verificationService.ts:162`）
- 现状：`session.withTransaction` 内对 **29 个集合** `deleteMany` 后物理删除用户文档。其中包含
  `device_trackings`、`security_events`、`auth_sessions`、`registration_invites`（用户侧）、
  `linuxdo_credit_orders`、`api_key_billing_events`、`translation_logs` 等。
  **只有 `audit_logs` 被刻意排除**（G2-30 注释）。
- 后果：删号即"洗白"——同一人换邮箱/邀请码即可重来，因为**设备、行为、IP、信用、邀请码使用链路全部消失**。
  这正是需求 (d) 要禁止的。
- 建议改法：
  1. 新增 `deletedAt`（时间戳）+ `accountStatus: "deleted"`（扩枚举），`deleteUser` 改为**软删除**：
     写 `deletedAt`、清 `password/passwordHash/password*/totpSecret/backupCodes/passkeys` 等凭据、
     `tokenVersion: $inc`、用户名/邮箱按需改成 `deleted_<id>` 释放唯一索引；**不删文档**。
  2. 级联清单拆成三类：
     - **保留并标记**（风控证据）：`device_trackings`、`security_events`、`auth_sessions`（改 `revokedAt`）、
       `api_key_billing_events`、`translation_logs`、`registration_invites`、`cdks`、`audit_logs`；
     - **真正删除**（用户内容/隐私）：`api_keys`、`access_tokens`、`oauth_*`、`account_identities`、
       `workspaces`、`voice_projects`、`tickets`、`user_preferences`、`short_urls` 等；
     - **保留但脱敏**：`bilibili_*`、`nexai_sync*`、`collaboration_sessions`。
  3. 保留项统一加 `subjectDeletedAt` 或在文档上留 `userId` 反查（现有索引已够：`security_events.userId`、
     `device_trackings.userId`）。
  4. **鉴权侧必须同步**：`authenticateToken.ts`、`auth.ts` 的 `authMiddlewareV2`、`wsAuthentication`
     需把 `deletedAt` 存在视为"不可登录"，否则软删除会变成"删了还能登"。
  5. 去重判定（`getUserByUsername/getUserByEmail`）要显式排除已软删除记录，
     或依赖改名后的 `deleted_<id>` 占位（推荐后者，语义更清楚）。
  6. **文案保持不变**（owner 于 2026-10-10 明确要求，见 RC-23）：
     `PrivacyConsentPanel.tsx:37`、`src/config/policyDocument.ts`、`src/templates/emailTemplates.ts`
     一律**不改**；因此实现侧必须保证「用户侧可见结果」与现有文案尽可能一致
     （用户列表里看不到、且不可自行恢复），差异只体现在数据库留存与管理员可见性上。

### RC-02（P0）没有"账户级人机验证闸门"，弹窗与后端鉴别都无从挂载

- 位置：`src/services/turnstile/providers.ts:486` `getCaptchaRequestPolicy()`、
  `src/controllers/auth/_state.ts:112` `verifyRequiredCaptcha()`
- 现状：判据是 `providers.filter(row => row.effective).length > 0` ——
  **"有没有供应商"决定"要不要验"，与请求方是谁、账户什么状态完全无关**。
  换句话说：一个已被确认刷量的账户，只要它按表单提交 captcha，待遇和正常用户一模一样。

- 建议改法：
  1. 引入**账户风险档** `riskTier: normal | watch | restricted | danger | banned`（详见 §3）。
  2. 新增闸门服务 `accountStepUpService`，输入 `(req, user, riskTier)`，输出
     `{ required: boolean; scope: 'none'|'sensitive'|'all-writes'|'all'; challengeId?: string }`。

### RC-03（P0）现有令牌模型撑不起"每次操作验一次"

- 位置：`ipVerificationService.issueToken`（`:283`）/ `verifyRequestToken`（`:764`）、
  `ipVerificationTokenModel.ts`、`runtimeConfigDefaults.ts:389`
- 现状：首访令牌绑定 `(fingerprint, ipAddress)`，TTL 40 分钟，`verifyRequestToken` **只校验存在与未过期**，
  同一张令牌在 40 分钟内可无限次复用；captchaToken 本身是一次性的，但只用在下发挑战那一刻。
- 后果：即便把"危险账户"接到首访闸门上，一次验证也能换来 40 分钟的免验证 —— 与"每一次操作都验证"相反。
- 建议改法：新建**单次挑战令牌** `step_up_challenges`（见 §4.3），与首访令牌并存、互不替代：
  - 字段：`challengeId`（随机）、`userId`、`riskTier`（签发时快照）、`routeKey`（方法+路由模板）、
    `payloadHash`（body 摘要，防"验一次、改内容重放"）、`issuedAt`、`expiresAt`（建议 120 秒）、
    `consumedAt`（原子单次消费）、`provider`、`ipAddress`、`fingerprint`。
  - 消费用 `findOneAndUpdate({ challengeId, consumedAt: null, expiresAt: { $gt: now } }, { $set: { consumedAt } })`，
    **原子单次**，并发重放只有一个成功。
  - 建 TTL 索引 `expiresAt` 自动清理，与 `ipBanModel` 同口径。

### RC-04（P1）账户数据模型没有任何风险字段

### RC-05（P1）注册反滥用缺"人/设备/IP"三个维度

- 位置：`registrationHandlers.ts:33-120`、`userRepository.ts:22` `buildNewUser`、`registrationInviteModel.ts`
- 现状（已有）：`fingerprint` 必填且 ≤512、四份政策逐项勾选、人机验证、主流邮箱白名单、
  `reserveAuthEmail` 冷却、验证码 5 次上限、邀请码校验 + 消费回滚。
- 缺口：
  1. **邮箱不做规范化**：`buildNewUser` 原样存 `email`（`userRepository.ts:22-34`），
     `getUserByEmail` 走精确匹配 ⇒ `User@Gmail.com` / `user+1@gmail.com` / `u.s.e.r@gmail.com`
     可各注册一个。这是最廉价的批量注册途径。
  2. **没有 IP / 指纹 / 设备维度的注册计数**：同一 IP 或同一指纹在 N 小时内注册 K 个账户没有闸门，

  3. **邀请码使用记录不含来源**：`RegistrationInviteUse`（`registrationInviteModel.ts:4-11`）只有

  1. 邮箱规范化：`trim().toLowerCase()`，并维护 gmail 点号/`+tag` 的归一化键（`emailCanonical`）

  2. 新增 `registration_attempts`（或复用 `security_events`）：记 `ipAddress`、`fingerprint`、

  3. 闸门：同 IP 24h 内成功注册 > N、同指纹 > M、同 `emailCanonical` 前缀变体 > K 时，
     拒绝或降级为「人工审核 / 必须邀请码」。
  4. 邀请码消费时把 `ipAddress` / `fingerprint` 一起写进 `usedBy`。
  5. 注册成功即调一次 `evaluateAccountRisk`（§4.2），把初始 `riskTier` / `riskScore` 落库。

### RC-06（P1）历来登录 IP 的 risk score 从未沉淀到账户

### RC-08（P1）前端没有"逐步验证弹窗"的编排层

- 位置：`frontend/src/components/ManagedCaptcha.tsx`（页面内嵌控件）、
  `frontend/src/api/api.ts:171`（仅识别 `403 IP_VERIFICATION_REQUIRED`）
- 现状：人机验证是**页面自己渲染控件、自己持令牌、自己提交**的模式；
  全局只广播一个 `IP_VERIFICATION_REQUIRED` 事件。没有"全局弹窗 + 挂起请求 + 验证后继续"的编排。
- 后果：需求 (b) 的前端一半（"每一次操作都弹窗")没有承载物。
- 建议改法：
  1. 新增全局 `StepUpGateProvider`（挂在 `App.tsx` 的 Provider 层）+ `useStepUp()`；
     收到 `403 STEP_UP_REQUIRED` 时把**原始请求**放进队列，弹 `ManagedCaptcha scenario="step_up"` 的模态框，
     解出挑战后换取单次令牌并**重放该请求**。
  2. **重放安全**：只对**幂等请求**（GET/HEAD/OPTIONS/PUT/DELETE）自动重放；
     POST/PATCH 必须在弹窗前提示用户"请重新提交"或由调用方显式传 `allowReplay: true`
     —— 与 `api.ts` 现有重试策略（`:190` 只重试幂等请求）保持同一条原则。
  3. 队列要有并发上限与去重：连续 10 个请求同时被挑战，只能弹**一个**弹窗，其余等待同一结果。
  4. 用户取消/超时要有明确出口（返回原错误 + 提示），不能静默吞掉。
  5. WebSocket / SSE / 静态资源**不走这条链路**（§4.6）。

### RC-09（P1）"每一次操作"的定义缺失，直接实现会打死应用

- 位置：全站中间件顺序（`src/app/assembly.ts`）
- 现状：无定义。
- 风险：若字面执行"后端每一次操作都鉴别"，则 `GET /api/user/me`、`GET /api/tts/history`、
  列表轮询、`/api/status` 心跳、WebSocket 升级全部要带一次性 captcha 令牌 ——
  一次页面加载几十个请求就是几十次人机验证，且**脚本/原生客户端（PiliPlus / Synapse-Client）无法弹窗**。
- 建议定义（写进 §3 的矩阵，并由运行时配置控制）：
  - `sensitive`（默认）：`POST/PUT/PATCH/DELETE` 全量 + 明确列出的敏感读
    （导出、下载、API Key 列表、会话/设备列表、账单）；
  - `all-writes`：所有 `POST/PUT/PATCH/DELETE`，读放行；
  - `all`：写 + 读都要求（仅用于"确认被盗号、正在被大规模自动化使用"的极端情形，且**必须**给白名单：
    健康检查、静态资源、认证/登出/验证挑战自身、WebSocket 握手）。
  - 无论哪档，**GET 类读在 `danger` 档采用"限流收紧 + 只读降级"，不采用每请求 captcha**，
    因为 `ManagedCaptcha` 无法对自动轮询工作。
  - 原生客户端：走 `Authorization: Bearer` 时若被判定需 step-up，返回
    `403 { code: "STEP_UP_REQUIRED", unsupported: "interactive" }`，由客户端自行降级为只读，
    **不要**让原生客户端卡在一个永远弹不出的弹窗上。

     同时要保证新上报不把新 id 当成新设备直接判风险。
  5. 合规：分量摘要属于设备信息，需同步 `src/generated/privacyDataMap.ts`（CI 卡漂移）。

#### RC-17（P1）没有「拼车 / 共享账号」检测，也没有对应处置

- 位置：`src/models/deviceTrackingModel.ts:54`（唯一索引 `(userId, deviceFingerprint)`，已有「一账户多设备」计数基础）、
  `src/models/authSessionModel.ts:39`（`(userId, deviceKey, lastActivityAt)` 索引）、
  `src/services/authSessionService.ts:264`（`revokeAllAuthSessions`，现成的处置手段）
- 现状：数据层完全支持查「这个账户有几台设备、几个 IP、几个活跃会话」，
  但**没有任何阈值、没有定时统计、没有任何自动处置**。管理端也没有相应按钮。
- 后果：需求「防拼车（多设备、多 IP 短期高并发）→ 共享账号一网打尽」无落点。
- 建议改法：
  1. 新增 `account_access_signals`（或直接由 `account_ip_signals` + `device_trackings` + `auth_sessions` 聚合）：
     统计窗口内 `distinctDeviceCount` / `distinctIpCount` / `distinctCountryCount` /
     **`concurrentSessionCount`** / `requestsPerMinute`。

     这是**区分「拼车」与「正常多端」的关键指标**：正常用户设备再多也是交替使用，拼车是持续同时在用。
  2. 规则建议三条件联立（缺一不可，否则误报率不可接受）：
     `distinctDeviceCount ≥ N` **且** `distinctCountryCount ≥ 2` **且** `concurrentSessionCount ≥ M`
     → `riskFlags: ACCOUNT_SHARING_SUSPECTED`，按配置升 `restricted`（先验证）或 `danger`（直接处置）。
  3. 处置（对应需求「全员封禁/一网打尽」）：`danger` 档执行 `revokeAllAuthSessions(userId)`
     —— 所有设备一起下线 —— 并强制全员 step-up；连续命中则升级为 `banned`。
  4. **必须给合法多设备场景留白**：`role` 枚举里已存在但从未参与判定的 `"trusted"`
     （`userStorageTypes.ts:18`；仅被管理端筛选与 OAuth 页面文案引用，
     `adminUserListHelpers.ts:43/324`、`OAuthAuthorizePage.tsx:83`）正好可以启用为
     「经管理员确认的多设备账户」豁免标记，否则会误伤真实多端用户（手机+平板+两台电脑是常态）。
  5. **反例防护**：企业/校园 NAT 会让大量无关用户共享出口 IP，因此 IP 维度只能做**加权**、
     不能单独判定 —— 与 §4.6 已有原则一致。
  6. 隐私：设备清单一类聚合结果只在管理端可见；用户侧最多展示「当前活跃设备」。

### 维度三：API 调用异常

#### RC-18（P1）API 滥用检测只有「每分钟固定额度」，没有突发与节奏判据

- 位置：`src/middleware/apiKeyAuth.ts:81`（`apiKeyRateLimiter.consume(keyId, doc.rateLimit)`）、
  `src/models/apiKeyModel.ts:32`（`rateLimit` 默认 60/min）、
  `src/middleware/routeLimiters.ts:162`（`RateLimitMetricsRegistry`，只记 429 指标供观测）
- 现状：限流是固定额度（令牌桶），`RateLimitMetricsRegistry` 是**观测**组件，不影响判定。
  没有任何判据看「突增速率」（相对该 key 自身基线）或「请求节奏规整度」（爬虫的等间隔特征）。
- 后果：需求「突发异常高频请求、规律性爬虫节奏」没有检测手段。
- 建议改法：
  1. 新增 `api_usage_windows`（`keyId`/`userId` × 分钟桶）：记 `count`、`endpointHistogram`、
     `interArrivalMean` / `interArrivalVariance`（滑动计算，不存原始时间戳数组）。
  2. 两条判据：
     - **突增**：`currentWindow / p95(last7d windows)` 超阈值 → `SPIKE`；
     - **节奏**：`cv = σ/μ < 0.15` 且样本数 ≥ 30 → `ROBOTIC_CADENCE`
       （人工操作间隔方差大，脚本轮询/爬取间隔极规整，这是低成本高信噪比判据）。
  3. 先跑观察期（结果只进 `api_usage_windows` 与 `security_events`），
     阈值稳定后再接自动处置 —— 对齐 `nexaiSecurityService` 的 `MONITOR` 档设计思路。

#### RC-19（P1）API Key 只有开/关两态，没有「降速 / 降 Tier / 临时封禁」载体

- 位置：`src/models/apiKeyModel.ts:36`（只有 `enabled: boolean`，无等级概念）、

- 现状：需求里的「降速（Rate Limit）、临时封禁或注销 Tier 权限」没有载体 —— 要么全开要么全关，
  而「立即吊销」是唯一可用的重手段。

  3. 新管理员动作 `API_KEY_REVOKE`（需求原文「API Key 立即吊销」）走 RC-07 的统一出口 + 审计。
  4. `danger` 档账户的**全部** Key 由 `accountRiskService` 统一置 `suspended`，而不是逐个手工处理。
  5. 归因：吊销/降速必须写 `reason` 与 `source`（`auto:SPIKE` / `auto:ROBOTIC_CADENCE` / `manual:<operatorId>`），

### RC-22（P0）取证保留与调查调取链路（“给政府机关调查使用”的落地）

软删除只解决“数据还在”，不解决“能安全、可追溯地交出去”。本项是**本任务真正的交付物**。

1. **保留期**：软删除记录**不设 TTL**（与 `audit_logs` 60 天口径不同，参考 `policyDocument.ts:385`）。
   必须显式写明保留期与依据，不能“默认永久”而没有依据。
2. **TTL 集合无法被软删除拦住**（**最容易漏的坑**）：
   `ipBanModel.ts:31`、`accessTokenModel`、`ipVerificationTokenModel`、
   `verificationTokenModel`、`proxycheckRiskCacheModel`、`authEmailCooldownModel` 等
   都建了 Mongo TTL 索引。**TTL 在数据库内部删除，不受应用层 `subjectDeletedAt` 控制**。
   方案（二选一，需 owner 定，见 D8）：
   - (a) 去掉 TTL，改由应用层定时任务清理，清理前先查 `legal_holds`；
   - (b) 保留 TTL，但在命中 `legal_holds` 时把文档**搬移**到不受 TTL 约束的保留集（如 `forensic_archives`）。
   推荐 (a)：逻辑单一，符合“不再有东西绕过保留判定”的目标。
3. **法律保留 hold**：新增 `legal_holds`（`scope: user|fingerprint|ip`、`value`、`caseRef`、
   `issuedBy`、`issuedAt`、`expiresAt`、`reason`）。命中 hold 的对象**禁止任何物理删除**
   （含 TTL 与管理员硬删）；`softDeleteService`、`deleteUser`、所有清理任务都要先查 hold。
4. **访问控制**：软删除数据默认对**所有管理员隐藏**；只在 `superadmin` + 专页（待登记到
   `src/config/adminPages.ts`，参照 `ip-ban` / `ip-risk-logs` 的登记方式）可见。
   普通 `admin` 看得到“有记录被删除”，看不到内容 —— 与现有 adminScope 分档一致。
5. **取证导出**：新增 `POST /api/admin/forensic/export`，按 `userId` / `ip` / `fingerprint` / 时间窗
   导出，产出带 SHA-256 校验和的归档（参照 `policyConsentService` 的 checksum 思路，
   但需覆盖**多集合**并固定字段顺序）。导出本身也是一次受审计事件。
6. **审计每一位访问者**：查看 / 导出 / 恢复软删除数据，一律写 `audit_logs` **与** `security_events`
   （谁、何时、什么范围、什么理由）。现有 `audit_logs` 只有 60 天（`policyDocument.ts:385`），

## 2.3 逐步验证的供应商选择（第四轮需求）

> 需求：**被标记账户的人机验证一律默认走 trycap（Cap）或 Cloudflare Turnstile，
> 并支持在 `/admin/captcha-providers` 前后端可改。**

### RC-24（P0）现有场景机制**无法限制供应商**，必须新增 `step_up` 场景 + 供应商白名单

#### 现状与关键证据

| # | 事实 | 位置 |
| --- | --- | --- |
| 1 | 场景枚举写死 3 个：`default / first_visit / standalone`，没有“被标记账户”这一场景 | `src/services/turnstile/types.ts:92/94/96` |
| 2 | 场景只控制**权重**与**策略**，不控制**候选集合**：先按 `effective`（enabled + 凭据齐 + 配额未耗尽）过滤，再按 `effectiveScenarioWeights[scenario]` 出权重 | `providers.ts:238`、判定 `:275-276`、过滤 `:322`、candidates `:330-336` |
| 3 | **权重 0 ≠ 排除**：`pickWeightedProvider` 在 `total <= 0` 时退化为**等概率抽取**；`failover` 只看 `priority`、`round_robin` 不看权重 | `allocation.ts:319`、回落分支 `:330-333` |
| 4 | 前端场景枚举也硬编码，且分布在四处 | `captcha-providers/types.ts:7`、场景清单 `:253-284`（`CAPTCHA_COVERAGE`）、草稿默认 `ProvidersTab.tsx:124`、`ManagedCaptcha.tsx:59` |

**结论**：需求里的“**一律**走 trycap 或 Turnstile”**不能靠现有机制实现**。
把 hCaptcha 权重设为 0 依然可能被选中（事实 3），在 `failover` / `round_robin` 策略下权重根本不参与。
必须新增一个**每场景供应商白名单**，它是硬约束而不是概率。

#### 建议改法

1. **新增场景** `step_up`（标签「被标记账户逐步验证」）：
   - `CaptchaScenario` 扩为 4 个（`types.ts:92/94/96`），
   - `normalizeStoredScenarioWeights`（`models.ts:202`）改为遍历 `CAPTCHA_SCENARIOS` 常量
     —— **不再手写数组**，否则下次加场景会重踩同一个坑，
   - 前端 `types.ts:7/78/87`、`ProvidersTab.tsx:124`、`ManagedCaptcha.tsx:59` 同步。
2. **新增白名单字段**（落在 allocation policy 文档，与 `scenarioStrategies` 并列）：
   ```ts
   scenarioProviderAllowlist: Partial<Record<CaptchaScenario, CaptchaProviderId[]>>
   ```
   - `DEFAULT_ALLOCATION_POLICY`（`allocation.ts:95`）默认设为
     `{ step_up: ["trycap", "turnstile"] }` —— **正好是需求要求的默认组合**；
   - 归一化新增 `normalizeScenarioAllowlist()`，与 `normalizeScenarioStrategies()`（`:183`）同形：
     去重、剔除非法 provider、空数组视为“未设置”（否则一个空数组会把该场景变成无候选）。
3. **生效点**：`collectCaptchaProviders()`（`providers.ts:238`）在 `effectiveRows` 之后、
   构建 `candidates`（`:330`）之前，取 `scenario` 的白名单做**交集**；
   白名单未设置的场景行为**逐字节不变**（向后兼容）。
   同时 `providers` 快照新增 `allowedForScenario: boolean`，让管理端能显示“这家在本场景被排除”。
4. **前后端共用同一常量**：`step_up` 这个字符串必须来自**同一份定义**
   （后端 `CAPTCHA_SCENARIOS` → 前端通过 `secure-captcha-config` 或构建期生成物获取），
   不允许后端返回 `"step_up"`、前端写 `"stepUp"` 这类字面量分叉 —— 仓库已有同类教训
   （`CAPTCHA-08` 的字段名不一致，见 `docs/audit-2026-10-07-captcha-lifecycle.md`）。
5. **与逐步验证闸门联动**（RC-02/RC-03）：
   - 后端 `stepUpGuard` 返回 `403 { code: "STEP_UP_REQUIRED", scenario: "step_up" }`；
   - 前端 `StepUpGate` 用 `ManagedCaptcha scenario="step_up"`（而非现在的 `standalone`）；
   - 后端在 `POST /api/step-up/challenge` 校挑战时，**重新校验该账户当前是否仍需 step-up**，
     且校验场景仍为 `step_up`（防止前端传 `default` 拿到更宽松的供应商集）。
6. **白名单耗尽时：`fail_closed`（owner 已定 2026-10-10，D11）**，且**不引入 hCaptcha 后备**
   （owner 已定，D12）。具体行为必须写死成下面四条，否则“失败关闭”会变成“静默放行”或“用户被卡死却不知道为什么”：
   - 判定：`step_up` 场景的 `candidates` 交集为空（trycap/turnstile 都 `effective=false`）时，
     **不得**回落到全局 enabled 列表、不得回落 `default` 场景、不得签发任何绕过令牌；
   - 对**被标记账户**：写操作一律 `403 { code: "STEP_UP_UNAVAILABLE" }`（带 `supportEmail`，
     复用 `providerAuthErrors` 的契约形状），并降为只读；**绝不静默放行**；
   - 对**未被标记账户**：`default` / `first_visit` / `standalone` 场景**完全不受影响**
     （hCaptcha 仍照常在这些场景服务）—— 失败关闭只作用于 `step_up`，
     不能把全站可用性绑到 trycap/Turnstile 上；
   - **告警与逃生舱**：进入该分支时必须按 `logger.error` + 可告警信号输出（不是 warn），
     并在 `/admin/captcha-providers` 概览处显示“step_up 白名单已耗尽”的红字提示；
     恢复手段 = 管理员在面板修凭据/配额，或**有审计地**临时调整白名单（调整走既有 PUT 契约，
     自动进 `audit_logs`），不另做“一键绕过”后门。
7. **上线前置（硬条件）**：`trycap` 与 `turnstile` 必须**凭据齐**且配额未耗尽，
   否则 `effective=false`（`providers.ts:320-322`），白名单交集为空、直接落入第 6 条的 `fail_closed` 分支。
   自托管 Cap 需先确认 `readProviderCredentials("trycap")` 的 siteKey/secret/endpoint 已配。
   **`fail_closed` 的代价必须提前告知运维**：trycap/Turnstile 双挂时，被标记账户的写操作会全停
   （读仍可用，未标记账户不受影响）—— 这是有意为之，不是故障；但必须告警，不能靠用户报障才发现。

### 第一层：接入层网络与设备防刷

#### RC-25（P1）真实 IP 强校验：解析链已存在，但需要加固与部署前提固定

- 位置：`src/utils/trustProxy.ts`（`parseTrustProxySetting`）、`src/app/assembly.ts:240`（`app.set("trust proxy", ...)`）、
  `src/utils/ipUtils.ts:25-45`（`extractRealIP`：优先 `req.ip`，否则回退头部）、
  `src/app/assembly.ts:125`（注释已声明“只取 TCP 层地址”）
- 现状：代理跳数解析、`req.ip` 优先、头部回退路径都已存在。
- **残留风险**：`extractRealIP` 在拿不到 `req.ip` 时**会回退到可伪造的头部**（`ipUtils.ts:38` 自己的注释就写着
  “在未走 CF 的部署或 trust proxy 配置使 req.ip 失效时可被伪造，影响封禁/限流/用量统计”）。
  一旦回退发生，`ipBanCheck` / 限流 / 用量统计全部建立在可伪造的地址上 —— 伪造 `X-Forwarded-For`
  即可给他人“刷出”封禁，或把自己伪装成干净 IP 绕过封禁。
- 建议改法：
  1. `TRUST_PROXY` 必填化：生产环境未配置时**启动直接抛错**（rather than 静默回退）。
  2. 回退分支收紧：只有从**可信代理**（TCP 对端命中 `TRUST_PROXY` 声明的网段/跳数）来的请求才允许读头部；
     否则**不回退**，直接用 TCP 地址（宁可将 NAT 后的多人归为一个 IP，也不接受一个可伪造的值）。
  3. `ipBanCheck` 的 CIDR 匹配与 Redis 同步黑名单保持现有语义，但封禁写入口要统一到 RC-07 的出口并记下“判据是哪个地址”。

#### RC-26（P1）IP 风险需从“两档”扩为“三档 + 硬切断”，并把 WebRTC 异常接上

- 位置：`src/services/ipRiskService.ts:113`（`buildIpRiskDecision`）、
  `src/config/runtimeConfigDefaults.ts:503-504`（`challengeRiskScore=66` / `blockRiskScore=90`）、
  `src/security/ipBlockPage.ts`（现有封禁/风险拦截页面）、
  `src/models/proxycheckProbeReportModel.ts`（WebRTC/出口 IP 探测落库）
- 现状：只有「挑战 / 封禁」两档，且**封禁仅由首访闸门产出**（`caller === "first_visit_gate"`）；
  普通 API 调用路径只 `report`，不拦截。
- 缺口：
  1. “中风险→人机验证”已实现（challenge），但**只作用于首访**；已登录用户的中风险出口不再复查。
  2. “高风险→切断连接 + 渲染拦截页”目前只在首访且仅在写库成功时发生；
     `manualBanIp` 失败时降级为挑战（合理），但没有告警。
  3. **WebRTC 泄露异常完全未接入**：探测数据只在表里，无任何闸门消费。
- 建议改法：
  1. 三档定义与 §3 的风险档对齐：低→放行；中（机房/VPN/高风险出口）→ `ManagedCaptcha` 或 PoW 挑战；
     高→写 `IpBanModel` + 渲染拦截页。
  2. 将 `shouldBlock` 从“仅首访闸门”扩展到**已登录请求的中阶复查**（按账户风险档控制频率，避免每请求外查）。
  3. WebRTC 异常（`proxycheckProbeReportModel` 的 mismatch/可比性判据）接入 `account_ip_signals`（RC-06），
     作为账户风险分的一路信号，而不是直接封禁 —— 探测报告是**客户端上报**，单独作为封禁判据就是新攻击面
     （与 `nexaiSecurityService.ts:162` 的既有原则一致）。

#### RC-27（P1）昂贵端点限流：矩阵已有，缺的是“双键 + 并发”约束

- 位置：`src/middleware/routeLimiters.ts`（64 个定义，`ttsGenerate` / `transcribe` / `authLogin` / `authRegister` / `cdict*`）、
  `src/services/sharedRateLimitStore.ts`（Redis / 内存档）
- 现状：路由级限流**已存在**，但主要是单键（按 IP 或按用户）与固定窗口/令牌桶。
- 缺口（按需求逐项核对）：
  1. `/api/tts/generate` 与 `/api/transcribe`：需要**`User ID + IP` 双键**与**突发并发上限**，
     否则同一账号换 IP 即可并行刷算力；而纯按 IP 会把 NAT 后的正常用户算作滥用。
  2. `/api/auth/*`：已有 `loginAttempts` 锁定（`_state.ts` 的 15 分钟锁）+ 限流，
     但**没有指数退避**；且 `loginAttempts` 是**进程内存 Map**，多实例下不同步（单实例无影响，扩容后就漏）。
  3. `/api/cdict/donate/claim`：需确认其专属频次（需求写“每 IP 每小时 10 次”）。
     现有 `cdict*` 系列限流器（`cdictIngress`/`cdict`/`cdictTrusted`…）是按“信任等级 + 安装 ID”分桶的，
     **需要一个面向 claim 的专用桶**（不与翻译类请求共用）。
- 建议改法：把这三个点写成**声明式限流定义**（复用 `limiterFromDefinition`），双键用 `keyGenerator` 组合
  `userId + ip`；并发用已有的后台任务注册表（`backgroundTaskRegistry`）计数并拒绝超限；
  指数退避与锁定状态**存 Redis（有则用）/ Mongo（无 Redis 时）**，不再只靠进程 Map。

### 第二层：核心资产与消费配额风控

#### RC-28（P1）预算熔断只做了“扣减”，缺 80% 预警与账户级总预算

- 位置：`src/services/apiKeyBillingService.ts:281/467`（`balanceCredits: { $gte: costCredits }` 原子预扣）、
  `src/models/apiKeyModel.ts:41-46`（`billingMode` / `balanceCredits` / `totalChargedCredits`）、
  `src/services/linuxDoCreditService.ts`（充值）
- 现状：**100% 阻断已具备** —— 余额不足时原子条件更新失败即为拒绝，且是并发安全的。
- 缺口：
  1. **80% 软预警没有实现**：没有“即将耗尽”事件、也没有通知（前端只能看到余额数字）。
  2. **账户级预算缺失**：配额只挂在单个 API Key 上，一个账号开 5 把 Key 就是 5 倍预算。
  3. 第三方商用 Key（OpenAI / Fish Audio）的**上游账单熔断**没有与用户预算联动：
     上游额度耗尽时应当变成“全局降级/排队”，而不是继续对用户报错。
- 建议改法：
  1. 新增 `quota_events`（或用 `security_events`）：余额跨过 80%/100% 阈值时各写一条，一条只写一次（去重键 `keyId + 阈值 + 账期`）。

#### RC-33（P0）输入侧 WAF：**必须豁免邮件系统 API**（本轮新增的硬要求）

  1. 在 `securityBypassPolicy.waf` 增加：

     `/api/email` 的写操作已是 superadmin 级 + 路由级限流，

     WAF 豁免的是**扫描**，不是**输出编码**，两者不能相互替代。
  4. 同时入 `securityBypassPolicy` 的**一致性校验**通道：`securityPolicy.ts:54` 注释提到

     否则可能是“静态规则与路由模块声明不一致”，会让豁免静默失效。

## 2.5 成本封锁与零信任极限制约（第六轮需求）

### ⚠ 必须先裁决的两项

#### 裁决一：RC-38 要求的“不提供原因/倒计时/申诉”与仓库既定契约正面冲突

需求原文：“系统文案固定显示‘服务维护中’，不提供封禁原因、不提供倒计时、不提供申诉入口。”

| `Synapse/CLAUDE.md`「处罚态契约」 | 封停（`ACCOUNT_SUSPENDED`）与工单封禁（`TICKET_PERMISSION_BANNED`）**都带稳定 `code`**，前端据此弹申诉入口；“新增任何「拒绝用户」的分支都要先问一句「前端怎么识别它」” |

#### 裁决二：RC-41 的“IP 跳变即全站踢出”会大规模误伤移动端与双卡用户

需求原文：“安全会话期间若检测到 IP 跳变（**即使只是同城不同网段**）…立刻全站踢出下线。”

- 移动网络（4G/5G）在基站切换、WiFi↔蜂窝切换、双卡待机时**分钟级换出口 IP 就是常态**；
  同城跨网段更是常见。按“任一跳变即踢”实现，结果是：**用户在手机上做一次敏感操作后就被登出**，
  且由于还要“失效所有派生 Token”，会连带把其它设备一起踢下线。
- 仓库里**已经有更好的现成判据**：`mobileTokenRiskService.isGeoJump()`（按国家/省，纯函数、已单测）
  与 `auth_sessions.ipLocation` 台账。它们的粒度是“国家/省”，不是网段。

**建议（需 owner 选）**：
1. （推荐）**设备绑定 + UA 严格校验立即失效；IP 变化只做风险信号**，按 RC-15 升档 ——
   即“UA 细微变化 = 立即失效”（防令牌被拿到另一环境重放），而“IP 跳变 = 升档 + 可按档位升级为踢出”。
2. 分客户端：`auth_sessions.clientType` 已区分 `web` / `PiliPlus` / `Synapse-Client` / `Project-Lumen`，
   移动客户端天然换网 → 可只对 `web` 做严格绑定。
3. 真要做“任一跳变即踢”，至少先跑观察期、并给用户可解释的提示（与裁决一相关）。

### 第二层补充：全生命周期资源配额封锁

#### RC-36（P1）动态 PoW 按调用加压：先纠正术语，再决定复用还是新造

- 位置：`src/services/turnstile/cap.ts` + `capEndpoint.ts`（**trycap 就是自托管的 Cap，本身就是 PoW 型供应商**）、
  `src/services/turnstile/providers.ts:486`（`getCaptchaRequestPolicy`）、
  `Synapse/CLAUDE.md`（“非关键第三方脚本…**在验证类页面禁用（会与验证码 PoW 抢主线程）**”）
- 需求原文写的是“SHA-256 碰撞”，**术语不成立**：PoW 是 **hashcash 式前像难度**（找 nonce 使
  `sha256(challenge||nonce)` 前缀为 N 个 0），不是“碰撞”（碰撞是找两个同摘要的不同输入，无法用作工作量证明）。
  实现时必须按前像难度做，否则“难度”无法校准也无法验证。
- 缺口：现有 PoW 是 **一次性挑战**（解一次换一张令牌），不是“每次调用前算一次”；
  且现有 `step_up`/`first_visit` 场景是按会话生效的（RC-03 已指出 40 分钟可复用）。
- 建议改法（与 RC-03 合流，不另造一套）：
  1. 把 PoW 作为 **`step_up` 挑战的一种解法**：`POST /api/step-up/challenge` 返回
     `{ type: "pow", difficulty, challenge }`，客户端算完提交 `nonce`，服务端验难度后签发**单次**令牌。
     这样“每次调用前算一次”由已有的单次令牌机制天然保证（RC-03）。
  2. 难度分档：新号（< 7 天）/ 未绑卡 / 异常账号才加压（需求给出的触发条件），
     目标耗时 2～5 秒 —— **难度必须以客户端实测回传为准做自适应**（移动端 CPU 差 10 倍以上，
     固定难度会让低端机等 20 秒）。
  3. 必须走 trycap/Cap 能力，不另写一套 PoW 客户端（供应链与主线程竞争风险已在 CLAUDE.md 记录）。
  4. 与 RC-24 一致：`step_up` 的供应商白名单默认 trycap/Turnstile；PoW 路线只在 trycap 可用时启用。

#### RC-37（P1）违规次数升级为“第 2 次违规冻结 7 天”

  3. **内存异常看门狗 + SIGKILL** —— 没有；grep 不到 `SIGKILL` / `memoryUsage` / `rss` 类判据。
- 建议改法：
  1. 每用户活跃上限 = 1（需求指定）；在入队处按 `userId + status ∈ {queued,running}` 计数。
  2. 全局总时长：每个任务带 `deadline`，后台任务注册表（`backgroundTaskRegistry`）统一扫描超时任务。
  3. 内存看门狗：**不能只看 `process.memoryUsage().rss`** —— 那是**整个 Node 进程**的共享值，
    一个转写任务吃内存会把所有任务判死（包括无辜的 TTS）。正确做法是对**子进程**单独计量
     （转写/pandoc 本就是子进程，见 `mediatool` 的 yt-dlp/ffmpeg 调用），或对任务做采样增量归因。
     否则“异常内存波动即 SIGKILL”会变成随机杀任务。
  4. “扣除当日任务额度”：必须写成**幂等**扣减（与 `apiKeyBillingService` 的预扣同口径），
     否则 SIGKILL 与重试交错会重复扣。

### 第三层补充：物理级零信任

#### RC-40（P1）安全会话 TTL 从 10 分钟压到 3～5 分钟

- 位置：`src/services/profileUpdateVerificationService.ts:28`（`PROFILE_VERIFICATION_TTL_MS = 10 * 60 * 1000`）、
  `src/utils/securitySession.ts:15`（注释写明“同一会话在 10 分钟 TTL 内可用于多次敏感操作”）
- 现状：10 分钟，且**校验不消耗**（同一会话可反复用于多个敏感操作）。

  1. TTL 收到 300000ms（与需求 3～5 分钟对齐），做成**运行时可配**（走 `runtimeConfigService`）。
  2. 是否改为**一次性消费**（用一次即失效）：需求未要求，但“多种敏感操作共享一个 10 分钟会话”

#### RC-41（P1）安全会话 IP/UA 绑定与全站踢出（**必须选粒度**，见上文裁决二）

- 位置：`src/utils/securitySession.ts:26-41`（`getSecuritySession` 只校验 `userId + token`）、

#### RC-42（P1）蜜罐端点（honeytokens）与静默标记：路径空闲，但有三处必须隔离

- 位置：`src/routes/index.ts`（路由注册表 + `validateRouteGovernance` / `validateRouterMiddlewarePresence`）、

  `scripts/governance/check-openapi-drift.js`
- 现状（已核实）：`/api/v1/*` 与 `/api/debug/*` **完全未被占用**，可以直接做蜜罐路径，不会与现有路由冲突。
- 三处必须隔离，否则蜜罐会误伤真实流量或卡住 CI：
  1. **openapi-drift**（`check-openapi-drift.js`）：蜜罐路由**不要**写 `@swagger` 注释 ——
     一旦写了就会被要求同步进 `openapi.json`，而它本来就不应该出现在文档里。
  2. **admin SPA paths / legacyApiRedirect**：新挂载必须按 `earlyModules.ts` 的注册表格式声明
     `isPublic`（否则治理校验报错）；且要确认不会把 `/api/v1/...` 当成前端页面 308 走。
  3. **安全旁路**：蜜罐必须**列进 `shouldBypassSecurityComponent`** 的 ipBan/ipVerification 旁路，
     否则一个已被封 IP 的扫描器会先被 `ipBanCheck` 挡住、永远触不到蜜罐（污染判据：你分不清
     “没人扫”与“扫了但被前置拦了”）。
- 返回假数据的风险（需在实现前定，见 D19）：假响应**不得**包含看似真实的他人个人信息
  （否则对真的权利请求者构成误导），建议只返回结构合法但无意义的占位值 + 固定埋点标识。
- 静默标记黑名单：写入 `IpBanModel`（IP）+ `device_trackings`（指纹）+ `security_events`（事件），
  并走 RC-07 的统一出口 —— 不要直接 `updateMany` 到用户表。
- 必须记审计：蜜罐命中是“高置信恶意信号”，误标代价高（真用户不会访问 `/api/debug/dump`，
  但**管理员工具/旧客户端可能**）→ 命中先写审计与告警，自动封禁阈值可配。

#### RC-43（P2）Tarpit 随机高延迟：方向正确但属于自伤型手段

- 位置：需新建；现有可复用件：`src/middleware/routeLimiters.ts`（限流）、`sharedRateLimitStore`
- 需求：“在所有核心业务端点悄悄加入 5～10 秒的随机高延迟”。
- **风险（必须在实现里处理）**：被拖延的请求仍然占用**一个连接 + 一个事件循环任务**。
  在 Node 单进程模型下，“把 1000 并发蜜罐请求各拖 8 秒”等于把服务端自己拖死 ——
  这是对攻击者零成本、对平台高成本的交换，与“拉高攻击者成本”的初衷相反。
- 建议改法：
  1. **只对已确认的蜜罐/黑名单对象生效**，不对“疑似”对象全站生效。
  2. 加**并发硬顶**（如全局最多 20 个 tarpit 连接），超顶的请求直接立即断连，不延后。
  3. 延迟必须 `await` 异步计时器，**绝不**用同步阻塞（本仓已有“主线程争用”教训：CLAUDE.md 提到
     Clarity 等脚本在验证页会与 PoW 抢主线程）—— 同步延时会让**整个进程**停摆。
  4. 并在指标里暴露“当前被 tarpit 的连接数”，否则它会成为下一个“看着像偶发超时”的难查故障。
  5. 建议先只对 **RC-42 命中对象** + `initialDelayMs` 上限 2 秒跑观察期，确认不自伤再放宽。

### RC-45（P0）`routeKey` 对齐陷阱：`req.route` 在早期中间件里**恒为 undefined**

- owner 指出的问题：§4.3 要求把挑战绑定到 `routeKey`（`req.route.path`），但 `accountStepUpGuard` 是
  **全局前置中间件**，它执行时路由匹配尚未完成 —— Express 只在**具体命中某条路由 handler 的阶段**
  才挂 `req.route`。在该位置读 `req.route.path` 必定得到 `undefined`，令牌根本签不出来（或全员撞同一个 `undefined` 键）。
- **这条审计成立**（与仓库既有教训同族：`check-openapi-drift` 注释里那句“swagger-jsdoc 静默丢弃”也属
  “你以为拿到了元数据，实际没拿到”的家族）。
- 修正设计的 3 条硬规则（写入 §4.3/§4.4）：
  1. **不得**用 `req.route.path`。`routeKey` 由以下优先级取得：
     - 优先：路由级 metadata（本仓已有路由注册表 `src/routes/index.ts` 与 `routeModules/*`，
       可在模块声明里带上模板名）；
     - 回退：`req.baseUrl + req.path` 再**归一化**（把 CUID/UUID/ObjectId / 纯数字段
       替换为 `:id`，否则 `/api/resources/a1b2` 与 `/api/resources/c3d4` 会被当成两个不同的 routeKey，
       使 payloadHash 绑定形同虚设 —— 攻击者换一个 :id 就绕过了）。
  2. **归一化函数必须单测**，覆盖：纯数字、ObjectId(24hex)、含连字 UUID、多余斜杠、
     带 query、带尾斜杠、写在 URL 里的 `%2F`。
  3. 校验时**重算** routeKey 并与令牌内的比对，**不信任**客户端传回的值
     （否则客户端直接声明 `routeKey: "/api/user/me"` 来把高危路由的令牌用在低危路由上）。
- 验收：新增用例“同一路由不同 :id → 同一 routeKey”、“不同路由 → 不同 routeKey”、
  “早期中间件位置下 routeKey 非 undefined”。

### RC-46（P0）并发挑战击穿：需引入短时效 **Step-up Grant**，不能为每个请求各签一枚挑战

- owner 指出的问题：前端并发多写请求（如同时 PUT/POST 两个关联资源）会拿到多个不同 `challengeId`；
  用户只过了一次验证，重放 B 时因 A 已被单次消费而报无效 —— 用户看到的是“验证通过了但操作依旧失败”。
- **这条审计成立**：§4.3 的单次挑战令牌只解决“防重放”，没解决“一次人机验证服务多个挂起请求”。
  两个目标本身矛盾（单次 vs 多请求），必须引入中间层。
- 修正设计（写入 §4.3）：
  - 新增 **`stepUpGrants`**：用户完成一次人机验证后，签发一枚 `grant`，
    绑定 `userId + routeKey 集合 + 指纹 + IP`，**TTL 30 秒**（极短窗口），
    允许多个挂起请求**依次原子兑换**（`findOneAndUpdate` 递减 `remainingUses`，并发安全）；
  - 每个业务请求仍然**自己带一个** `payloadHash`，兑换时校验：
    `grant.routeKey` 包含本次请求的 routeKey，且**未重复消费同一 payloadHash**（防同一请求重放）；
  - `grant` **不是**“验证一次免 30 秒”—— 它只允许“已经排在队列里、且已被用户看到的那批请求”通过，
    新发起的请求仍然走完整挑战（否则它就退化成 RC-03 批判的那个 40 分钟可复用令牌的短命版）。
  - 前端配套（§4.5）：队列并发上限 + 同一 `(routeKey, payloadHash)` 去重；
    队列为空时立刻丢弃 grant，不缓存到过期。
  - 单次消费仍然保留于**挑战令牌**层：`challengeId` 一兑换就作废，`grant` 只承载“已通过的那一次验证”。
- 验收：并发 3 个不同请求 + 1 个重复请求 → 3 个成功、1 个被 payloadHash 去重拒绝；
  第 4 个新请求（grant 已耗尽）→ 重新弹窗；`grant` 过期 → 重新弹窗。

### RC-47（P0）**已引入的真实漏洞**：软删除改名释放唯一索引 = “注销再注册”洗白风险档

- owner 指出的问题（**成立，且是本文档 B1 实现造成的**）：`softDeleteUser` 把 `username`/`email`
  改成 `deleted_<id>` 以释放唯一索引，攻击者随即用**同一邮箱重新注册**；
  注册查重只比规范化邮箱，而旧账号已被改名 → 查不到 → **注册成功，`riskTier` 归零**。
  这正好推翻了 RC-01 的目的（保留风险历史）。
- 根因：本文档把「释放唯一索引以便用户重注」当成了需求，但 **“同一个邮箱重新注册”本身就不应该被允许**：
  如果这个邮箱上曾有风险记录，“注销→重注”就是零成本洗白；
  即使无风险记录，“注销后立即用同一邮箱重注”也不是正常用户行为，而是规避手段。
- 修法（写入 RC-01/RC-21）：
  1. 新增 **`blocked_identities`**（墓碑表）：`{ emailCanonical, username, userId, reason, blockedAt,
     releasedBy?: string|null }`；软删除时**写入墓碑**，`username` 与 `email` **不再释放**。
  2. 注册/绑定/改名查重时**同时查 `user_datas`（未删除）与 `blocked_identities`**；
     命中墓碑 → 拒绝并回稳定 `code`（如 `IDENTITY_RETIRED`），文案不暴露风控细节但告知“该邮箱不可用，请联系支持”。
  3. 保留唯一索引：既然不释放，`user_datas` 上的 `username`/`email` 唯一索引可以**保持原值不动**
     （反而更简单，也不再有改名步骤带来的并发窗口）。
  4. 人工释放：`releasedBy` 只为“真的误删、已人工核验”的恢复路径服务，且必须过安全会话（RC-32）+ 审计（RC-35）。
  5. 反向风险：墓碑表会积累 PII（邮箱）。按 RC-22 的口径属“安全与风控”类，需在 `privacyDataMap` 里登记
     （`docs/governance/privacy-data-map.json` 的 `evidence`/`retention`），不能做成“看不见的永久邮箱名单”。
- 验收：软删除后（a）`getUserByEmail` 查不到 → 但（b）**注册同一邮箱被拒**；
  （c）人工释放后可以重注；（d）释放行为进审计。

### RC-48（P0）WAF 豁免粒度：**已由字段级白名单满足** —— 禁止前缀级 bypass

- owner 指出的问题（**方向正确，但实测结论与本档 RC-33 原方案相反**）：
  完全豁免 `/api/email` / `/api/outemail` 会把服务暴露在超大 Payload DoS、
  邮件头注入（CRLF）、模板注入风险下；应只豁免正文字段。
- **实测结果（决定性）**：无需新增任何 bypass ——
  `src/middleware/wafMiddleware.ts:309+` 已经调用 `addWafWhitelist("html", "text", "content", "message", "markdown", ...)`，
  即 **具体字段级**豁免已经存在（注释写明“适用于本身就会包含特殊字符的业务字段（如 HTML 内容）”）。
  而两端的 HTML 字段名正好命中：
  - `/api/email` 的 `{ from, to, subject, html, text }` → **`html` / `text` 已豁免**；
  - `/api/outemail/send` 的 `{ to, subject, content, from, displayName }` → **`content` 已豁免**。
- **`F:\\Repositories\\GitHub\\Chloemlla\\scripts\\lib\\fork-sync\\email` 的依赖已核实**：
  它（`send.mjs`）打的就是 `POST /api/outemail/send`，body 为
  `{ to, subject, content, from, displayName }`，`content` 是全 HTML（内联 `style=`、
  `box-shadow:0 18px 60px rgba(...)`、`role="presentation"` 表格、`<a href>`、`<code style=...>`）。
  该字段已在白名单内，**当前就是通的**；只要“不走前缀 bypass + 不把 `content` 从白名单里拿掉”，就不会弄坏它。
- 因此 RC-33 **修正为**：
  1. **不新增** `securityBypassPolicy.waf` 的 `/api/email`、`/api/outemail` 前缀条目（那正是 owner 担心的无条件绕过）；
  2. 改为**保护性回归测试**：构造与 fork-sync 相同形状的 HTML（含内联 style / rgba() / 表格 /
     `<code>`）POST 到 `/api/outemail/send`，断言**不被 WAF 拦**；
  3. 同时断言**基础防护仍在**：`to` / `subject` 这些**未**白名单的字段仍被扫描
     （这正是 CRLF / 邮件头注入的拦截面）、body 大小上限仍生效、JSON 解析层溢出检查仍生效；
  4. 白名单变更（有人以后把 `content` 删掉）应由该用例卡住，而不是靠口头约定。
- 顺带纠正：本文档 §2.4 的 RC-33 写的是“**必须新增前缀豁免**”，**该结论错误，以本条为准**。

## 2.7 加固终态与自动迁移（第八轮 + 落地实现）

### RC-45 补遗：路由模板的退化策略（防过度通配）

o `req.baseUrl + req.path` 归一化漏掉未预期的正则边界（如 `/api/tools/v1/export.json`、带特殊字符），
必须遵守：
1. 在 `assembly.ts` 注册 `accountStepUpGuard` 时，**优先使用已声明模板的路由包装器**，
    或在路由文件顶部显式声明路径模板；
2. 遇到**未显式标注模板且归一化不确定**的路由，降级为 **exact match 严格单路由**；
    宁可让少数路由的 step-up 令牌不能跨实例复用（用户重新验一次），也不得过度通配把
    “一个窄路由的令牌”升级成“一类路由的通行证”。

### RC-46 补遗：改用 **服务端签名的 challengeTicket**，不信任前端上报的 routeKeys

原设计 `POST /api/step-up/grant { routeKeys[], token, provider }` 存在**“任意路由申领”漏洞**：
客户端可直接上报 `routeKeys: ["/api/command", "/api/admin/env"]` 骗取高危路由的短效通行证，
也可虚报数量（声称需 5 次）把 Grant 放大成批量发射器。闭环方案：

1. **发 Ticket**：业务请求被拦时，403 响应体不再是裸字符串，而是**服务端 HMAC 签名**的
   `challengeTicket`（内含 `userId`、**服务端归一化后的 `routeKey`**、时间戳）；
2. **凭 Ticket 兑换**：`POST /api/step-up/grant` 必须提交 `challengeTickets[]`；
   服务端**验签后**从 Ticket 里提取 `routeKeys` 作为该 Grant 的允许集，
   **坚决不信任前端自行上传的未签名数组**；
3. **配额硬顶**：`remainingUses` **严格等于合法 Ticket 数量**，且上限 **5**。
   （这就是 D22 的最终结论；对应 §4.3 的 grant 模型需增加 `allowedRouteKeys` 与 `ticketIds` 字段。）
4. Ticket 自身也要限次数/时效（建议 120s，与 challenge 对齐），防止“批量收集 Ticket → 一次性兑一大枚 Grant”。

### RC-47 落地（已完成）：部分唯一索引 + 墓碑 + **自动迁移**

#### 与 owner 建议的一处技术修正（重要）

owner 建议把唯一索引改为
`{ email: 1 }, { unique: true, partialFilterExpression: { deletedAt: { $eq: null } } }`。
**方向正确（部分唯一索引就是对的），但过滤条件必须改**：

> 本模型的 `deletedAt` 是**数字 0** 表示未删除（见 `utils/softDeleteState.ts`），
> 而 `{ $eq: null }` 在 MongoDB 里只匹配「字段为 null **或字段缺失**」，**不匹配 0**。
> 若照写，则**全部存量活跃账号都不在索引范围内** —— 邮箱唯一性直接被取消，
> 比它要解决的洗白问题更严重。

实际实现（`userService.ts` 与迁移模块共用同一常量）：
```ts
{ $or: [{ deletedAt: 0 }, { deletedAt: { $exists: false } }] }
```
语义等价于 `activeUserFilter()`（`$in: [0, null]`），但改用 `$or` + 等值/`$exists`
这组**部分索引最保守的运算符子集**，避开“表达式被拒→索引建不出来”的线上故障。

#### 线上索引选项变更的真实风险（已处理）

Mongoose 默认 `autoIndex=true`。线上已存在 `email_1` / `username_1`（unique、无 partial）。
同一个 key spec、不同 options 时 MongoDB 报 `IndexOptionsConflict` / `IndexKeySpecsConflict`：
**新索引建不出来、旧索引还在**（开发环境正常、线上静默失效）。
处理方式：
- 迁移里显式 **drop 再 create**（幂等）；
- 首次启动可能出现**一行** Mongoose 索引冲突日志（autoIndex 抢在迁移前尝试）——
  属已知且无害（`unhandledRejection` 只记不退），迁移完成后后续启动不再出现。

#### 自动迁移：**状态判定 + 落库标记 + 终态短路**

- 运行器：`src/services/migrationRunner.ts`（启动期自动跑，接在 `connectMongo()` 之后、
  `UserStorage.initializeDatabase()` 之前）；
- 台账集合：`schema_migrations`（**这就是 owner 要的“数据库里做好标记”**）：
  - 标 `applied` ⇒ 后续启动**只读一次标记就跳过**，不再检查索引、不再执行动作；
  - 无标记 / `failed` / `blocked` ⇒ 才进入只读状态判定；
  - 需复查时用 `MIGRATIONS_REVERIFY=true`（显式打开，**不常开**）。
- 状态机（只读判定，决定要不要动手）：
  `fresh` / `already_migrated`（无动作，只补标记）/ `legacy_full_unique`（drop+create）/
  `partial_incomplete`（补齐）/ `duplicates_active`（**blocked**，绝不先删数据）。
- 跨实例：`schema_migrations` 上的一枚原子锁（compare-and-set；upsert 撞主键即被占用），
  **不依赖 Redis**（启动期 Redis 可能未就绪），且已 `applied` 的实例根本不抢锁。
- 失败语义：**不让进程退出**（多数失败需人工介入，全站不可用比特性缺失严重），
  只告警；观测通道 = 启动日志 + `pnpm run migrate:rc47-indexes -- --dry-run`。
- 手工入口：`scripts/migrations/rc47-user-datas-partial-unique-indexes.ts`
  （`--dry-run` / `--force` / `--reverify`），**与启动期共用同一实现**，
  不重复写第二份索引逻辑（两份实现必然漂移）。

#### 遗留（必须知道）

- 早期版本把软删除账号的 username/email 改名为 `deleted_<id>` 并**释放过邮箱** ——
  那段窗口内如果真发生了“注销后重注”，墓碑无法追溯（原值只能从 `deletedOriginal*` 回填，
  已改名且无 `deletedOriginalEmail` 的账号无法还原）。迁移脚本/模块会从
  `deletedOriginalEmail` 回填墓碑，把这个窗口尽量封上。
- B1 至今未部署到生产的前提下，上述窗口实际为 0；部署后不会再有该窗口（已不再改名）。

### 事实校正（先纠正，再开工）

| 说法 | 代码实际 | 结论 |
| --- | --- | --- |
| 「前端计算动态 Nonce、时间戳校验与短期挑战票据」 | **已存在但只覆盖两个域**：`nexaiSigning` / `cdictSigning`（HMAC + `maxDriftMs` 时间窗，`off/soft/enforce` 三档） | 这是一套现成的**动态验签**范式，可直接复用其判定形状；但它不覆盖站内风控路由，且时间窗内**同一签名可重放**（无 nonce 台账） |
| 「PoW 哈希碰撞」 | 术语不成立（见 RC-36）：PoW 是 **hashcash 式前像难度**，不是碰撞 | 按前像难度实现，难度要按客户端实测回传自适应 |
| 「接入 IP 风险评分（阻断 IDC/代理/Tor）」 | 已有：`CHALLENGE_FLAGS = vpn/proxy/tor`、`blockRiskScore=90`、首访闸门可封禁；**已登录请求不复查**，机房 IP **被显式排除**在挑战判据外（`ipRiskService.ts:57`） | 判定零件齐，**接线只在首访**（RC-14/RC-26/RC-56） |
| 「比对 WebRTC 与出口 IP」 | 探测**确实在采集**（`proxycheckProbeReportModel`、`ipTelemetryService`） | 无消费方（RC-26.3 → RC-56） |
| 「环境指纹识别无头浏览器」 | Canvas/WebGL 只上行复合哈希（RC-16）；`navigator.webdriver` 之类**未消费** | 作为**信号**而非判据（客户端可伪造，RC-57） |
| 「不要一次性返回整份核心大 JSON」 | 列表端点已普遍 `.lean()+select()` + 分页下推 Mongo；但**没有统一的响应体量上限**，导出类端点仍是整份 JSON | 缺的是「治理闸门 + 导出流式化」（RC-58） |
| 「敏感文字渲染为矢量 Canvas/SVG」 | 无 | **不采用**（理由见 §4.6 新增行）：废掉可访问性/复制/搜索，且挡不住截图型抓取 |
| 「按 User ID + IP 双键限流」 | 限流器 64 个，主要是**单键**；`loginAttempts` 是**进程内存 Map**（多实例不同步） | 与 RC-27 同一条，本轮并入 B3/B9 落地 |

### RC-54（P1）请求端动态证明：现有工具体系缺「每次调用都重新花成本」

- 位置：`src/services/ipVerificationService.ts:283/764`（首访令牌 TTL 40min、`verifyRequestToken` 只校验存在与未过期）、
  `src/services/turnstile/cap.ts` + `capEndpoint.ts`（trycap = 自托管 Cap，**本身就是 PoW 型供应商**）、
  `src/config/runtimeConfigDefaults.ts` 的 `nexaiSigning`/`cdictSigning`（HMAC 请求签名 + 时间窗）
- 现状：三种“证明”各自割裂 —— 首访令牌**一次验证换 40 分钟免验证**；
  PoW 是**一次性挑战**（解一次换一张令牌）；请求签名只护住 nexai/cdict 两个域且**无 nonce 台账**
  （时间窗内同一签名可重放）。没有一种机制表达「**这一次调用**是刚刚花过成本的」。
- 后果：脚本只要过掉一次挑战，就能在窗口内无限调用；这正是「破解算法后仍要算动态签名」要解决的问题。
- 建议改法（**与 RC-03/RC-36 合流，不另造体系**）：
  1. 复用 RC-03 的**单次挑战令牌**作为唯一载体：每个需要证明的请求兑换一枚、`consumedAt` 原子消费；
  2. PoW 作为 `POST /api/step-up/challenge` 的一种解法（`type: "pow"`），服务端只验难度、
     不验“客户端算得优雅不优雅”：`sha256(challenge||nonce)` 前缀零比特数 ≥ 声明难度；
     难度按**客户端实测回传**自适应（移动端 CPU 差 10 倍以上，固定难度会让低端机等 20 秒 → RC-36.2）；
  3. 挑战票据走 **服务端 HMAC 签名**（RC-46 补遗）：客户端只回传票据，不自行上报 routeKey/次数；
  4. nonce/时间戳重放保护**复用单次令牌**，不新建 nonce 台账：挑战 `challengeId` 唯一 + 原子消费，
     等价于“nonce 只用一次”，且比进程内 nonce Set 在**多实例下正确**（本仓多实例部署是常态）。
- 验收：同一挑战票据第二次兑换必失败；`grant` 用尽后新请求必须重新弹窗；
  伪造难度（声明高、实际低）被拒；重放同一 `payloadHash` 被拒。

### RC-55（P1）服务端会话上下文缺失：每个闸门各自查库/各自解释请求

- 位置：`src/middleware/authenticateToken.ts`（只挂 `req.user`）、`src/middleware/adminScope.ts`、
  `src/services/accountRiskService.ts`（本次新增）、`src/utils/ipUtils.ts:25-45`、`src/services/authSessionService.ts`
- 现状：风控要用的「这一次请求是谁、用什么设备、哪个 IP、属地、账户档位、step-up 状态」
  散在 `req.user` / `req.ip` / 各自的一次 Mongo 查询里。任何新闸门都要**重新拼一遍**，
  于是（a）同一请求里 IP 判定可能前后不一致，（b）每个闸门再多一次查库，
  （c）新增判据时无法回答「这次请求到底用的是什么上下文」。
- 建议改法：在认证之后、业务之前构建**一次性的服务端会话上下文**（请求期内存对象，**不落库**）：
  ```ts
  interface RequestRiskContext {
    userId: string;
    role: string;
    riskTier: RiskTier;
    stepUp: { required: boolean; mode; until: number };
    ip: { address: string; trusted: boolean; location?: string };
    device: { fingerprint?: string; uaHash: string; sessionId?: string };
    session: { id?: string; clientType?: string; createdAt?: number };
  }
  ```
  - 只读一次用户文档（`authenticateToken` 已有），**不再额外查库**；属地取会话台账已有值；
  - `trusted` 来自 `trustProxy`（RC-25）：回退到可伪造头部的地址必须显式标为不可信，
    后续闸门据此**只记信号、不做处罚**；
  - 所有闸门（step-up / 限流双键 / 审计 / 蜜罐）从这一个对象读取判定输入，
    并把它的快照（除 PII 外）写进审计，事后可解释。
- 验收：同一请求内多个闸门读到的 `ip.address` 与 `riskTier` **完全相同**；
  新增闸门不需要新增查库；上下文缺失时闸门 fail-closed 到「只记信号」。

### RC-56（P1）信誉阻断只作用于首访与注册：已登录请求不复查，WebRTC 异常未接线

- 位置：`src/services/ipRiskService.ts:113`（`shouldBlock` 仅在 `caller === "first_visit_gate"`）、
  `src/models/proxycheckProbeReportModel.ts`、`src/services/ipTelemetryService.ts`、

- 建议改法：

     由 step-up 闸门在**已登录**路径上按账户档位控制复查频率（如 `watch` 以上每 N 分钟一次），

  2. 机房/IDC 单独成规则（RC-14）：**注册 + 无邀请码**拒绝；`restricted` 以上出现 IDC 出口直接升档；

  3. WebRTC/出口 IP 不一致 → 写 `security_events` 作为**账户风险信号**（RC-06 聚合进 `riskFlags`），
     **不直接封禁** —— 探测报告是客户端上报，单独作为封禁判据就是新攻击面
     （与 `nexaiSecurityService.ts:162` 既有原则一致）。
- 验收：已登录请求在中期复查命中中风险时返回 `403 STEP_UP_REQUIRED`（而不是静默放行）；
  复查频率受配置控制（同账户 N 分钟内不重复外呼）；WebRTC 不一致只进信号与风险分。

## 3. 建议的账户风险分档与动作矩阵

`riskTier`（账户唯一档位，取值单调升级、可人工降级）：

| 档位 | 含义 | 触发（示例） | 强制动作 |
| --- | --- | --- | --- |
| `normal` | 正常 | 默认 | 现有表单级人机验证 + 首访闸门 |
| `watch` | 观察 | 新号 7 天内 / 近期登录 IP 风险分 60-79 / 单设备多账号 | 登录必验；风险分持续采样；管理端可见标记 |
| `restricted` | 受限 | 风险分 ≥ 80 / 命中 ≥2 个 flag / 多次 `RISK_BLOCKED` | `sensitive` 档每次操作验人机 + 限流额度减半 + 禁用高风险功能（导出/API Key/图床） |
| `danger` | 危险 | 风险分 ≥ 90 / 确认多开或自动化 / 管理员手工标记 | `all-writes`（可升 `all`）每次操作验人机 + 只读降级 + 存量会话强制重验 |
| `banned` | 封禁 | 管理员封停 / 严重违规 | 403 `ACCOUNT_SUSPENDED`（现有行为），不再给验证机会 |

**升降级规则**：自动升级只做 `normal → watch → restricted`，**`danger` / `banned` 必须人工确认或
由管理员开启的自动规则触发**（避免误封真实用户）；降级需要"观察窗口内无新命中"或管理员手动。

**`stepUpUntil`**：`restricted`/`danger` 档签名成一个到期时间，避免"永久每次验证"把用户卡死；
到期前若风险分仍高则续期。管理员也可给一个固定时段。

### 3.1 三维风控矩阵：规则 → 检测信号 → 现有落点 → 处置

| 维度 | 规则 | 检测信号（已有 / 需新增） | 现有落点 | 处置（按档位） |
| --- | --- | --- | --- | --- |
| **地域与网络** | 严格执行 Supported Regions | `ip.ts` 的 `country`/`region`；proxycheck `country`/`isocode`（已有） | 无（政策文本） | 注册拒绝 / 登录阻断 / API Key 吊销（RC-13） |
| 同上 | 机房数据中心 IP（ASN/IDC） | proxycheck `hosting`/`networkType`/`asn`、Scamalytics `is_datacenter`（已采集、无消费方） | 仅进 `risk` 分权重 | 注册拒绝（无邀请码时）；升档（RC-14） |
| 同上 | 瞬时跨地域跳变 | `auth_sessions.ipLocation`（已有）+ `isGeoJump()`（已有但仅移动端） | `mobileTokenRiskService` | 记录 + 提醒；`watch` 以上进 step-up（RC-15） |
| **行为指纹** | Canvas/WebGL 指纹比对 | `fingerprint.ts:110/129`（已采集，但只上行复合 hash） | `user_datas.fingerprints[]` | `FP_COMPONENT_DRIFT` / `FP_SHARED_ACROSS_ACCOUNTS` → 升档（RC-16） |
| 同上 | 防拼车（多设备/多 IP/短期高并发） | `device_trackings`、`auth_sessions`（数据已有，无阈值无统计） | 无 | 三条件联立 → `ACCOUNT_SHARING_SUSPECTED` → `revokeAllAuthSessions` + 全员 step-up（RC-17） |
| **API 调用异常** | 突发异常高频请求 | `apiKeyRateLimiter` 额度（已有）+ `RateLimitMetricsRegistry`（仅观测） | 固定额度 429 | `SPIKE` → 降速 / 临时封禁（RC-18/19） |
| 同上 | 规律性爬虫节奏 | 需新增：`interArrivalMean/Variance` | 无 | `ROBOTIC_CADENCE` → 降速 / 降 Tier |
| 同上 | 高频触发违规拦截 | IP 维度 `violationCount`（已有），账户维度缺失 | `ipBanModel` | 账户维 `ACCOUNT_ABUSE_*` → 进 `riskScore`（RC-20） |

三维矩阵是**信号来源**，`riskTier` 是**唯一处罚状态机** —— 否则会出现"IP 说封、账户说放行"的自相矛盾。

### 3.2 超级管理员豁免（fail-safe 基线，RC-44）

> owner 要求：**风控对超级管理员豁免**。
> 这是必要条件 —— 否则一套自动风控可以把运维者自己踢出平台，且没有任何人能把它改回来。

#### 豁免范围（必须“自动强制”类全免）

| 控制项 | 对 superadmin | 理由 |
| --- | --- | --- |
| 账户风险档自动升降（RC-06/RC-07） | **不参与自动升档**，`riskTier` 恒为 `normal`；`riskScore` 仍计算并入审计（看得到，不处罚） | 自动升档 + step-up = 管理员被自己系统锁死 |
| step-up 每次操作验证（RC-02/03/24） | **默认豁免** | 同上；且在 `danger` 档下连读都被降级时，管理员将无法操作面板处理事故 |
| PoW 加压 / 未绑卡限制（RC-36） | 不适用 | 管理员不是刷算力的风险面 |
| 交叉权限株连（RC-38） | 不适用 | 否则工单/上传全停时无法处理事故 |
| 对话与并发熔断 / 自动封禁（RC-29/RC-37） | 不参与自动封禁 | 仓库已有同类口径：`userService.incrementUserDailyUsageAtomic` 与 `libreChatQuotaService` 都只豁免 `admin`/`superadmin` |
| 登录指数退避与临时封禁（RC-27.2） | 不因失败次数自动封禁 | 锁死风险；改为“失败即发告警邮件 + 审计” |
| 蜜罐标记 / Tarpit（RC-42/RC-43） | **不对 superadmin 生效** | 管理员常用 `/api/debug/*`、批量导出、脚本化调用，命中蜜罐的概率远高于攻击者，误杀代价最大 |
| 安全会话 IP/UA 绑定全站踢出（RC-41） | **不适用全站踢出** | 管理员在移动网络/VPN 下运维是常态，踢出即失去控制权 |

#### 豁免**不**包括的三件事（否则豁免本身成盲区）

1. **交互式二次认证仍必需**：RC-32/RC-40 的安全会话（Passkey/TOTP/密码，TTL 3～5 分钟）
   **不豁免**。它不依赖风险判定，而是“本人确认”的取证链；将其豁免等于把“零信任”整个挖空。
2. **审计与告警不豁免**：豁免动作本身必须留痕。建议每次豁免拦截时写
   `security_events`（`eventType: "SUPERADMIN_RISK_EXEMPT"`，含被豁免的判据名、路由、风险分）。
   否则出事时无法回答“那十分钟管理员绕过了什么”。
3. **异常登录告警不豁免**：属地跳变、新设备登录仍要发提醒邮件（`loginHandlers.ts` 已有模板）。

#### 实现要点（避免“豁免”变成“提权”）

1. **唯一判据源**：新增 `isRiskExempt(user, { scope })`，只认 `role === "superadmin"`，
   不允许按 `trusted` / 邮箱后缀 / 用户 ID 白名单开洞 —— 后两者会把豁免变成可配置的“免死金牌”。
2. **硬编码不变量**：`softDeleteUser` 与批量删号必须继续拒绝删除**最后一个** superadmin
   （现有 `isLastSuperadmin` 检查已有，不要因本次改造而放宽）；
   对 superadmin 的删除/封停额外要求**安全会话**（RC-32）并写高优先级审计。
3. **可降级开关**：豁免可被环境变量/运行时配置**关闭**（用于故障注入验证风控本身），
   但默认必须开启，且关闭状态要在启动日志与面板上显式可见（否则“忘了开回去”没人发现）。
4. **不得由普通 admin 调整**：豁免行为只能由 superadmin 改（`adminScope` 已保证未登记前缀 fail-closed 只给超管）。
5. **反向风险告知**：superadmin 被剥夺豁免（如配置关闭）时，应在面板显式提醒“当前风控可能锁死你自己”。

#### RC-44（P0）超级管理员豁免基线（实现位置与验收）

- 位置：新增 `src/services/riskExemption.ts`；所有拦截/升档/处罚点调用同一判据；
  现有可复用的同类口径：`userService.incrementUserDailyUsageAtomic`、`libreChatQuotaService`
  都已把 `admin`/`superadmin` 排除在额度外；`adminScope.ts` 已保证未登记前缀 fail-closed 只给超管
- 验收（缺一条就不算完成）：
  1. `isRiskExempt` 是唯一判据源，只认 `role === "superadmin"`，**不接受**邮箱后缀 / ID 白名单 / `trusted`；
  2. 在 step-up 闸门（B3）、账户升档（RC-06/07）、PoW 加压（RC-36）、
     交叉株连（RC-38）、蜜罐与 Tarpit（RC-42/43）、安全会话全站踢出（RC-41）**每一处**都有调用；
  3. 每次豁免拦截写 `security_events`（`SUPERADMIN_RISK_EXEMPT`）+ 审计；

### 4.2 账户风险聚合 `evaluateAccountRisk(userId)`

- 输入：`account_ip_signals`（近 30 天）+ `device_trackings` + `security_events` + 账户姿态
  （MFA/指纹）+ 注册新鲜度。
- 输出：`{ riskScore: 0-100, riskTier, flags[], reasons[] }`。
- 调用时机：**登录成功后**（同步，用已有缓存，不外呼）、**每次风险事件上报后**（异步）、
  **管理员面板打开账户详情时**（实时）、**定时任务**（建议 6h 一轮，复用 `backgroundTaskRegistry`）。
- 幂等：写入 `riskUpdatedAt`，同分同档不重复写事件。
- 纯函数化：核心折算逻辑写成纯函数（输入事实 → 输出分档），便于 Jest 直测，不依赖 Mongo
  —— 仓库里 `mobileTokenRiskService.collectRotationRiskSignals` / `isGeoJump` 就是这个范式。

### 4.3 单次挑战令牌生命周期（RC-03 / RC-45 / RC-46）

> ⚠ **两条已修正的陷阱，实现前必须读**：
> - `routeKey` **不得**取 `req.route.path`（早期中间件下恒为 `undefined`）—— 见 RC-45，
>   改用路由级 metadata 或 `req.baseUrl + req.path` 归一化，且校验时**重算**而不信任客户端值。
> - 冰发多请求不能各签一枚挑战 —— 见 RC-46，需引入 **30 秒 TTL 的 step-up grant** 作为中间层。

```
前端                         后端
 │ 并发多个写请求（带会话）      │
 ├────────────────────────────►│ stepUpGuard：账户档位需要验证？
 │                             │   否 → next()
 │◄── 403 { code:"STEP_UP_REQUIRED", scenario:"step_up" } ─┐
 │ 全局弹窗（只弹一个，队列去重）                            │
 │ 解出 { token, provider }                               │
 ├── POST /api/step-up/grant { routeKeys[], token, provider } ──►
 │                             │ 校验 captcha → 签 grant
 │                             │   （TTL 30s，多人次兑换，绑定 userId+指纹+IP）
 │◄── 200 { grantId, remainingUses } ──┤
 ├── 重放挂起请求 + X-Step-Up-Grant: <id> + X-Payload-Hash ─►│
 │                             │ 原子递减 remainingUses
 │                             │ 校验 routeKey 在 grant 内 + payloadHash 未用过
 │◄── 200/4xx 原结果 ──────────┤
 │ 队列空 → 主动丢弃 grant（不缓存到过期）
 │ 新发请求（grant 已耗尽/过期）→ 回到弹窗
```

**要点**：
- 两层令牌职责分离：**challenge**（一次性，验验人机验证本身，TTL 120s）
  与 **grant**（短窗多人次，服务“已排队的同一批请求”，TTL 30s）；
- `grant` **不是**“验证一次免 30 秒”：它只放行**用户已经发起、且已经看到弹窗**的那批请求；
  队列排空即作废。否则它就退化成 RC-03 批判的“40 分钟可复用令牌”的短命版；
- 同一 `(routeKey, payloadHash)` 在一枚 grant 内**只能兑换一次**（防同一请求重放）；
- `routeKey` 取法与校验规则见 RC-45（归一化 + 服务端重算）；
- 消费必须**先消费后转发**：`findOneAndUpdate` 原子递减，失败即拒绝，避免 TOCTOU
  （仓库已有同类教训，见 `softDeleteRecord` 的 owner-in-filter 注释）；
- 挑战与 grant 的创建都要限流（复用 `routeLimiters.createLimiter`），防“无限弹窗”本身成为可用性攻击面。

### 4.4 后端中间件插入点

- 位置：`assembly.ts` 的 **API 路由相位**，在 `authenticateToken` **之后**、业务路由 **之前**。
- 顺序：`authenticateToken`（拿到 `req.user`）→ **`accountStepUpGuard`** → 业务。
- 豁免清单（必须显式，且进 `securityPolicy` 白名单机制，便于审计）：
  `OPTIONS`、`/api/health`、`/api/status`、`/api/auth/logout`、step-up 挑战端点自身、
  `/static/**`、WebSocket 升级、以及 `shouldBypassSecurityComponent()` 已登记的内部路径。
- 契约：
  - `403 { success:false, error:"需要完成人机验证", code:"STEP_UP_REQUIRED", scope, routeKey? }`
  - **必须带稳定 `code`**（`CLAUDE.md` 安全注意事项：处罚类不带 `code` 前端识别不了）。
- 鉴权解耦：`stepUpGuard` 只读 `req.user.riskTier`（登录时已随用户文档取出，无需额外查询），
  避免"每个请求再多一次 Mongo 查"。

### 4.5 前端编排（RC-08）

- 新增：`frontend/src/components/StepUpGate.tsx` + `frontend/src/utils/stepUpQueue.ts`。

| 想法 | 判定 | 原因 |
| --- | --- | --- |

## 7. 验证方式（按 `AGENTS.md` / 方法论）

- **本地零构建**：所有验证交 CI（`Node verification` / 后端 Jest / 前端 Vitest / 镜像 / CodeQL）。
- 静态自查（允许）：改动文件的花括号平衡、`git diff` 逐份核查。
- 判据（方法论 §五-36）：`check-runs` 用 jq 自判布尔 + 两次快照一致，不用 `--exit-status`。
- 每批必须带的回归测试：
  - B1：软删除后 `getUserByUsername/Email` 行为、鉴权拒绝、级联"保留/删除/脱敏"三分法各自断言；
  - B2：`evaluateAccountRisk` 纯函数表驱动（各风险分档边界）、`account_ip_signals` 幂等 upsert；
  - B3：挑战令牌单次消费（并发只有一个成功）、`routeKey`/`payloadHash` 不匹配拒绝、过期拒绝、
    豁免路径放行、`STEP_UP_REQUIRED` 契约形状；
  - B4：邮箱变体（大小写 / gmail 点号 / `+tag`）查重、同 IP 配额触发；
  - B5：多请求并发只弹一个弹窗、非幂等请求不自动重放、取消/超时出口；
  - B7：`isGeoJump` 公共化后原单测不回归；指纹分量漂移/跨账户共用判定表驱动；
    拼车规则三条件联立（分别缺一时不触发）；`ROBOTIC_CADENCE` 的 `cv` 边界值；
    Key `throttled`/`suspended` 下的额度与 `code` 契约；
  - B3/RC-24：`step_up` 场景的白名单**恒等于**候选集（把 hCaptcha 打开且权重调到最高也不出现）；
    白名单为空/命中全不可用时走 `fail_closed` 而非回落；
    `default` / `first_visit` / `standalone` 三个场景的候选集与旧行为逐字段一致（回归）；
    新增场景的落库往返（存 → 读）不被 `normalizeStoredScenarioWeights` 丢弃；
  - B8：**裸 `deleteOne` 治理闸门**（受管集合上出现裸删必须 CI 报错）；
    软删除后用户侧不可见 / 管理员默认不可见 / superadmin 可见；`legal_holds` 命中时
    （含 TTL 集合）任何路径都删不掉；取证导出带校验和且写审计；`status | softDeleteService` 幂等重删。
