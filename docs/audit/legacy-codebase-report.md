## Executive summary

- Current runnable state: Not locally executed; repository policy requires actual build/test commands to run in GitHub workflows.
- Main conclusion: The repository has substantial implemented functionality and several positive controls, but identity/session authority, secret handling, persistence ownership, test authenticity, and release promotion are split across incompatible paths. The most serious failures are deterministic rather than stylistic: browser cookie sessions are rejected by `/api/auth/me`, administrators can recover users' original passwords, MFA/runtime credentials are broadly persisted or projected, guest chat ownership can collide, and production deployment can bypass verification and report success after destructive failure.
- Highest-priority findings: Freeze unverified production promotion first (F-002/F-003/F-013/F-014), then repair the server-side auth/serialization boundary before widening cookie use (F-004/F-007/F-008/F-043-F-046), and remove recoverable password/MFA/runtime secrets from ordinary storage and response projections (F-029/F-030/F-035/F-046).
- Next smallest action: Make the production deployment job depend on required checks for the exact image digest and fail closed, while a separate security slice removes `strict-ssl=false` and prevents current-user/admin serializers from returning authentication material.

## System map

- User journeys: browser registration/login (password, TOTP, Passkey, OAuth), protected/admin navigation, TTS generation/history, chat, CDK/resource/admin operations, email, artifacts/log sharing, webhook ingestion, and WebSocket notifications.
- Browser boundary: a Vite/React SPA uses a shared Axios client plus multiple independent Axios/fetch paths, HttpOnly cookie sessions with some bearer exceptions, local/session storage, and a WebSocket query-token path. Auth state is instantiated in many hooks rather than owned by one provider.
- Application boundary: Express assembly applies core parsing/request IDs, security/CORS/Helmet/WAF/rate-limit/auth variants, routes/static delivery, and error handling. Startup initializes diagnostics, embedded Rust workers, permissions, Mongo/user storage, billing reconciliation, schedulers, HTTP, and WebSocket.
- Data authorities: Mongo `user_datas` is the main user authority; `runtime_config_settings` is the configuration authority with a mutable process cache; `USER_STORAGE_MODE` also permits MySQL/file modes; disk holds uploads/audio/share logs and fallback JSON. LibreChat currently has Mongo, process memory, and `data/chat_history.json` authorities without one concurrency protocol.
- Internal runtime units: the production image contains Node/Express, the built React SPA, and five Rust binaries (network, audio, file, data, security), optionally exposed as Compose sidecars or started in-process and reached through shared-memory/file-backed IPC or HTTP fallback.
- External trust boundaries: OpenAI-compatible providers, Mongo/Redis, Resend/Svix, GitHub, LinuxDo, DeepLX, IPQS/Scamalytics, IPFS/image-bed endpoints, public network/media providers, Docker Hub, GitHub Actions, SSH, and production Docker hosts.
- Delivery flow: pull requests run partially overlapping TypeScript/Jest/Rust/governance/browser/CodeQL jobs; the Docker workflow independently builds and publishes branch/short-SHA tags, then SSH-deploys, replaces containers, prunes images, and uploads a log. It is not promotion of the artifact proven by the required verification jobs.
- Principal failure boundaries: browser-to-session authority, middleware-to-controller auth context, administrator-to-secret storage, Express-to-Mongo/cache ownership, multi-instance persistence, webhook/provider retry semantics, process shutdown, image promotion, SSH host identity, and rollback/readiness.

## Root-cause clusters

- **Identity has no single authority.** F-004/F-007/F-008/F-040/F-043-F-049/F-060/F-061 show browser state, cookies, bearer tokens, WebSocket claims, IP identity, shared passwords, and three middleware families making different decisions. Repair order: define one request/session/admin context, remove secrets from its DTOs, then migrate every HTTP/WS route and frontend client to it.
- **Secrets are treated as ordinary application data.** F-016/F-029/F-030/F-035/F-037/F-046/F-050/F-059/F-076 share missing secret lifecycle controls: values are recoverable, broadly projected, logged, duplicated, or fetched over an untrusted TLS path. Central redaction alone is insufficient; storage, projection, transport, rotation, and custody must be designed together.
- **Mutable caches and multiple persistence authorities lack concurrency protocols.** F-006/F-032/F-033/F-041/F-055-F-057 cover mocked boundaries, stale configuration snapshots, repeated connection ownership, Mongo/memory/file chat state, webhook acknowledgement, and feature-local database reconnection. Establish one owner per datum and version/atomicity rules before decomposing files.
- **Retry, idempotency, and lifecycle behavior are best-effort.** F-001/F-002/F-014/F-042/F-052/F-055/F-056 combine ambiguous mutation replay, destructive deploy steps, competing shutdown handlers, and event delivery without durable acknowledgement/deduplication. The common fix is explicit state-machine transitions with stable operation IDs and verified terminal conditions.
- **The verification system tests replicas or bypasses real boundaries.** F-005/F-006/F-020/F-023-F-028/F-063-F-065 show ignored suites, global mocks, copied servers/algorithms, weak assertions, missing frontend execution, and no coverage baseline. This explains how concrete auth, storage, and release defects coexist with substantial test volume.
- **Release is an independent mutation path rather than promotion of a verified artifact.** F-002/F-003/F-012-F-014/F-062/F-066-F-071/F-075/F-076 show verification/deploy graph separation, weak host/artifact identity, mutable tags/bases, missing attestations, and absent readiness/rollback evidence.
- **Normative guidance and ownership drift from executable reality.** F-010/F-018/F-019/F-024/F-058/F-074/F-078/F-080/F-081 retain disabled/dead surfaces, mixed-responsibility units, stale scripts/specs/contracts, and unidentified ownership. Cleanup should follow consumer discovery and characterization, not size-only rewrites.
- **Performance and operations are weakly observable.** F-017/F-022/F-033/F-053/F-068/F-071/F-072/F-079 identify broad browser work, fragmented deadlines, redundant initialization, silent fallbacks, absent probes/metrics, and duplicated CI work. Runtime profiling is required before numerical performance claims.
