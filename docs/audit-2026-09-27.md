### SYN-01 — 管理操作口令残留 `NODE_ENV==="test"` 后门（默认口令 `admin`）

- **位置**：`src/utils/adminOperationPassword.ts:33`
  ```ts
  if (process.env.NODE_ENV === "test" && timingSafeStringEqual(candidate, process.env.TEST_ADMIN_PASSWORD || "admin")) {
    return true;
  }
  ```
- **类型**：认证绕过（环境错配触发）。
- **详细说明**：`isAdminOperationPasswordValid` 是命令执行（`commandService`）、以及多个管理写操作的口令闸门。
  当 `NODE_ENV==="test"` 时，只要提交口令等于 `TEST_ADMIN_PASSWORD`，或——在该变量未设时——等于硬编码字面量 `"admin"`，即通过校验。
  一旦生产/预发布环境被误配成 `NODE_ENV=test`（容器编排、CI 复用镜像、运维手滑都可能发生），
  攻击者用万能口令 `admin` 即可通过管理操作口令闸门。
- **佐证（同类问题已在别处被认定为缺陷并移除）**：`src/services/commandService.ts:523` 的注释明确记载
  `G7-39: the NODE_ENV === "test" && password === "wumy" hardcoded backdoor is removed. Any deployment with NODE_ENV=test would otherwise accept a universal admin password.`
  即：**完全相同的模式**在 commandService 里已被判定为必须移除的后门，但在 adminOperationPassword 里仍然存在，属加固遗漏。
- **建议改法**：删除这条 test 分支；测试用例改为在测试内部注入/桩掉 `config.adminOperationPassword`，
  或用一个只在 Jest setup 里显式设置、绝不落默认值的专用测试口令（且不提供 `"admin"` 兜底）。

### SYN-02 — `authenticateToken` 不校验 `disabled` 账户状态，与其它鉴权路径不一致

- **位置**：`src/middleware/authenticateToken.ts:39-41`
  ```ts
  if (user.accountStatus === "suspended") { return res.status(403)... }
  // 缺少：user.disabled 的检查
  ```
- **类型**：访问控制状态判定不一致（IDOR/越权邻域）。
- **详细说明**：用户模型确实有 `disabled` 字段（`src/services/userService.ts:90` `disabled: { type: Boolean, default: false }`）。
  另外两条鉴权路径都同时校验 `disabled` 与 `suspended`：
  - `src/middleware/auth.ts`（`authMiddlewareV2`）：`if ((user as any).disabled) return 403` **且** `if (accountStatus==="suspended") return 403`
  - `src/services/wsAuthentication.ts:57`：`if (!user || user.disabled || user.accountStatus==="suspended")`
  - `src/services/outEmailService.ts:166`：同时看 `disabled || suspended`

  唯独新版 `authenticateToken`（被 **36 个路由文件**引用，含 `commandRoutes`、`admin/shortlinks`、`analyticsRoutes` 等）
  只看 `suspended`。因此一个被置为 `disabled:true` 但未 `suspended` 的账户，仍能在这些路由上通过鉴权。
- **当前实际影响**：偏低——目前没有任何管理端把用户 `disabled` 置 true（在线封禁走的是 `accountStatus="suspended"`），
  `disabled` 是历史/遗留字段。但这是一处"语义已存在、判定却分叉"的一致性缺口：一旦将来把 `disabled` 接线用于封禁，
  这 36 个路由会静默漏封。
- **建议改法**：在 `authenticateToken` 的用户状态检查处补一条 `if ((user as any).disabled) return res.status(403).json({ error: "账户已被禁用" })`，
  与 `authMiddlewareV2` 对齐（见 SYN-04）。

### SYN-03 — `extractRealIP` 在 `req.ip` 不可用时无条件采信 `CF-Connecting-IP`

- **位置**：`src/utils/ipUtils.ts:41-44`
  ```ts
  const cfConnectingIP = req.headers["cf-connecting-ip"];
  if (cfConnectingIP && typeof cfConnectingIP === "string" && isValidIP(cfConnectingIP)) {
    return cfConnectingIP;
  }
  ```
- **类型**：客户端可控头导致 IP 伪造（影响封禁 / 限流 / 用量统计 / 同 IP 并发上限）。
- **详细说明**：主路径 `req.ip`（受 `trust proxy` 约束，默认不信任任何代理，见 `utils/trustProxy.ts`）是安全的。
  问题在回退分支：当 `req.ip` 校验不通过时，直接采信客户端可自带的 `CF-Connecting-IP` 头，
  **未验证请求确实来自 Cloudflare 边缘**（例如未校验对端属于 CF 的 IP 段）。
  在"未走 Cloudflare 的部署"或"`trust proxy` 配置使 `req.ip` 变为无效/缺失"的组合下，客户端可通过伪造该头控制被记录的 IP。
- **触发条件与影响**：需要 `req.ip` 先变无效才进入该分支，常规部署下 `req.ip` 恒有效，故实际风险偏低；但作为纵深防御应收敛。
- **建议改法**：仅在明确启用 Cloudflare 的部署（如 `TRUST_CLOUDFLARE=1` 或校验对端 IP ∈ CF 官方段）时才采信 `CF-Connecting-IP`；
  否则不要让一个客户端可写的头参与"真实 IP"判定。

### SYN-04 — 两套 JWT 鉴权中间件并存，校验项已分叉（可维护性/漂移风险）

- **位置**：`src/middleware/auth.ts`（`authMiddlewareV2` / `authenticateAdmin` / `authenticateSuperAdmin`）
  与 `src/middleware/authenticateToken.ts`。
- **类型**：Info（架构一致性）。两者都做 `jwt.verify(..., { algorithms: ["HS256"] })`（算法固定，无算法混淆风险，已确认），
  但**账户状态校验分叉**（SYN-02 即其后果），且各自实现 session touch 逻辑略有差异。
  `auth.ts` 顶部注释已声明"V1 委托 V2、避免双路径漂移"的意图，但 `authenticateToken.ts` 是第三条独立路径，未纳入该收敛。
- **建议**：让 `authenticateToken` 的状态检查与 `authMiddlewareV2` 完全对齐（至少补齐 `disabled`），
  或统一收敛到单一强制点，避免今后再度分叉。

## 三、已核验为稳健的安全面（无需改动）

- **命令执行**（`services/commandService.ts`）：白名单命令 + 危险字符预筛 + 硬编码命令映射 + `spawn(shell:false, argv 数组)` + 输出上限 + 超时；
  且已移除历史 `NODE_ENV=test` 万能口令（G7-39）。无命令注入面。
- **JWT**：签发/校验全程 `HS256` 固定算法（`utils/authToken.ts`、`middleware/*`、`services/*`），无 `jwt.decode` 用于鉴权决策，无算法混淆。
- **CORS + CSRF**（`middleware/corsMiddleware.ts`）：白名单精确匹配 + 通配子域受控正则；
  状态变更请求额外做 `requireAllowedOriginForWrites`（Origin/Referer 硬校验）叠加 SameSite=Lax。
- **WAF**（`middleware/wafMiddleware.ts`）：SQLi/XSS/命令注入/路径穿越四类检测，正则已按 ReDoS 加固（G1-01/19/20 有界量词），
  白名单字段走 relaxed 检查仍拦截攻击载荷（G1-03），URL 解码有层数与长度上限。
- **SSRF**（`config/fishAudioCatalog.ts::validateFishAudioProxyUrl` + `ttsProviderController`）：音频代理限 `https:` + 主机白名单（`*.fish.audio`）。
- **信任代理 / 真实 IP**（`utils/trustProxy.ts`）：默认不信任任何代理，生产未配置时打印告警；WS 升级路径与 HTTP 同口径；限流本机判定只取 TCP 层地址（G1-33）。
- **路径穿越**（`mediaTool/runtime.ts::relInsideRoot`）：normalize + 去前导斜杠 + 拒 `../`/`.` + `path.resolve` 后 `relInside` 二次核验；文件端点全在 `requireAdmin` 之后；上传 `sanitizeFileName` + 类型过滤 + 大小上限。
- **CSP**（`security/contentSecurityPolicy.ts`）：`script-src` 基于 nonce，无 `unsafe-inline`/`unsafe-eval`；`script-src-attr: none`。
- **配置/密钥治理**（`config/config.ts`）：生产强制 `JWT_SECRET ≥ 32` 且 `ADMIN_PASSWORD ≥ 12` 且非弱口令，否则启动报错；开发用临时密钥。
  EcoEnchants 运维/激活令牌使用独立于主站 JWT 的专用密钥，生产缺失即硬报错（G7-57）。
- **密钥落库**：`.env` 系列、`secrets/`、`*.pem` 均在 `.gitignore` 内且未被 git 跟踪，源码内未发现硬编码长随机密钥。
- **批量赋值**：`resourceService.updateResource` 走字段白名单；`artifactService.updateArtifact` 仅消费固定字段且 `findOne({shortId,userId})` 按属主收敛；
  `oauthController.createClient` 管理员闸门 + 强制覆盖 `ownerUserId`。
- **口令比较**：`adminOperationPassword.ts` 用 `crypto.timingSafeEqual`（定长缓冲 + 长度回校），恒定时。
