# RC-31 / RC-32 / RC-41 治理接线记录（2026-10-17）

> 范围：`docs/audit/10-10.md` 中 RC-31（按同意开放功能的覆盖补齐）、RC-32（敏感写端点的安全会话清单）、
> RC-41（其余调用 `hasValidSecuritySession` 的敏感端点接入异步绑定）。
> 约束：本机不构建/不测试/不装依赖；以下结论来自只读检索与静态接线，最终判据是 GitHub Actions。
> 本文只记录后端接线；前端与其它未授权文件需要的配合单独列在最后一节。

## 1. RC-31：9 个漏登功能键全部挂上同意闸门

判定契约保持不变：只认 `userId`（不回落设备指纹），每次请求实时读库（服务层不缓存），
未同意统一 `403 { code: "POLICY_CONSENT_REQUIRED", feature, missingAgreements, ... }`。

| 功能键 | 端点 | 挂载位置 | 备注 |
| --- | --- | --- | --- |
| `image-upload` | `POST /api/image-data/validate`、`POST /api/image-data/validate-batch`、`GET /api/image-data/info/:imageId`、`POST /api/image-data/record` | 每条路由的 `authenticateToken` 之后 | 该模块没有挂载级认证，逐路由挂 |
| `ipfs-upload` | `POST /api/ipfs/upload` | `optionalAuthenticateToken` + `ipfsApiKeyAuth` 之后，`uploadLimiter` 之前 | 用条件门禁：匿名 Turnstile 通道保持原行为，已识别 userId 时才校验 |
| `transcribe` | `/api/transcribe/**` | `postTamperModules` 的 `middlewares: [authenticateToken, requireFeatureConsent(...), transcribeLimiter]` | 认证来自挂载层，同意闸门紧跟在它后面 |
| `tts-generate` | `POST /api/tts/generate`、`POST /api/tts/jobs` | `optionalAuthenticateToken` + `ttsApiKeyAuth` 之后 | API Key / OAuth 通道也会注入 `req.user`，因此同一道门禁覆盖三种身份 |
| `deeplx-translate` | `/api/deeplx/**` | `router.use(authenticateToken)` 之后 | 整棵用户态路由统一门禁 |
| `shorturl` | `GET /api/shorturl/shorturls`、`DELETE /api/shorturl/shorturls/batch`、`DELETE /api/shorturl/shorturls/:code`；`POST /api/shorturl/public/create` | 用户路由在 `authMiddleware` 之后；公共创建在 `optionalAdminAuth` 之后用条件门禁 | 匿名公共创建、`/s/:code` 跳转保持公开 |
| `api-access` | `/api/apikeys/**`；`/api/oauth/authorize`、`/authorize/preview`、`/authorize/mobile/*`、`/userinfo` | API Key 路由 `router.use` 在认证/限流之后；OAuth 授权端点在各 `authMiddleware` 之后；`/userinfo` 在 `oauthTokenAuth()` 之后用条件门禁 | OAuth 的 client 凭据端点（`/token`、`/introspect`、`/revoke`）仍面向客户端，不按 userId 门禁 |
| `cdk-redeem` | `POST /api/cdks/redeem`、`GET /api/cdks/redeemed` | `authenticateToken` 之后 | 管理员 CDK 管理端点不属于“兑换”语义，未加门禁 |
| `data-report` | `POST /api/data-collection/collect_data`、`POST /api/collect_data`（同一 router 的两个挂载） | 限流器之后，`optionalAuthenticateToken` 之后用条件门禁 | 匿名客户端上报保持原行为；带登录态时要求本人同意 |

条件门禁：`requireFeatureConsentForAuthenticatedUser(feature)`（`src/middleware/featureConsent.ts`）。
未识别出 `userId` 时直接 `next()`；识别出则复用 `requireFeatureConsent` 的同一套判定与 403 形状，
避免出现“公开路径被 401”或两条门禁口径分叉。

## 2. RC-32：三类敏感写端点的安全会话覆盖

统一守卫：`requireSecuritySession`（`src/utils/securitySession.ts`），
先同步校验会话，再用同一枚已解析会话做异步属地绑定判定（不重复解析/查库），
失败分别返回稳定 code `SECURITY_SESSION_REQUIRED` / `SECURITY_SESSION_BINDING_CHANGED`。
所有目标端点原本就有 `auditLog`，守卫放在 `auditLog` 之后，因此**被拒绝的尝试也会进审计**。
另外把可能携带 `verificationToken` 的路由级审计改为 `captureBody: false`（命令 `/y`、`/execute`、
`/clear-history`、`/clear-queue`，环境变量删除，OAuth 密钥轮换，短链 AES_KEY 删除），
避免二次验证令牌被写进审计库；命令本身仍通过 `extractDetail` 留痕。

| 类别 | 端点 | 之前 | 现在 |
| --- | --- | --- | --- |
| 主密钥派生/查看 | `POST /api/admin/envs/reveal-key` | 控制器内 `hasValidSecuritySession`，403 无 code | 路由层 `requireSecuritySession`（稳定 code + 异步绑定），控制器内检查保留为纵深 |
| 环境变量变更 | `POST /api/admin/envs`、`DELETE /api/admin/envs`、`POST /api/admin/envs/delete` | 无安全会话 | 路由层 `requireSecuritySession` |
| 主密钥轮换 | `POST /api/admin/envs/rotate-aes-key` | 控制器内检查，403 无 code | 路由层 `requireSecuritySession` |
| 主密钥重加密 | `POST /api/admin/pixel/key-rotation/reencrypt` | 同步检查，无绑定 | `assertSecuritySessionBinding` + 失败审计 |
| OAuth 客户端密钥轮换 | `POST /api/oauth/clients/:clientId/rotate-secret` | 无安全会话 | 路由层 `requireSecuritySession` |
| 短链 AES_KEY 轮换 | `POST /api/shorturl/admin/aes-key`、`DELETE /api/shorturl/admin/aes-key` | 无安全会话 | 路由层 `requireSecuritySession` |
| 安全会话紧急撤销 | `POST /api/admin/envs/end-sessions` | 控制器内检查，403 无 code | 路由层 `requireSecuritySession` |

## 3. RC-41：其余敏感端点的异步绑定

裁决二落地方式不变：**UA 摘要**在签过名的 token payload 里，同步校验不匹配立即失效；
**IP 变化**只在敏感操作前做异步属地判定——同城异网只写 `SECURITY_SESSION_IP_CHANGED` 信号，
只有 `isGeoJump`（跨国家/省）才终止安全会话并 `revokeAllAuthSessions` 全站下线。

| 端点 | 文件 | 接入方式 |
| --- | --- | --- |
| `POST /api/command/y`、`/execute`、`/status`、`/clear-history`、`/clear-queue` | `src/routes/commandRoutes.ts` | 同步校验后 `await assertSecuritySessionBinding(req)`；403 带稳定 code |
| `GET /api/admin/system/redis/overview`、`/redis/keys`、`POST /redis/value`、`GET /redis/export` | `src/routes/admin/system.ts` | `ensureSecuritySession` 改为 async，内部执行绑定判定 |
| `POST /api/admin/user/profile/devices/:deviceKey/revoke` | `src/routes/admin/profile.ts` | 同步校验后绑定；失败 403 |
| `POST /api/admin/user/profile/email/send-code` | `src/routes/admin/profile.ts` | 同上 |
| `POST /api/admin/user/profile`（带 `verificationToken` 时） | `src/routes/admin/profile.ts` | 会话有效后再做绑定；绑定失败即拒绝本次资料修改 |
| `POST /api/admin/user/profile/linked-accounts/:provider/start`、`/unlink`、`POST /account-merge/confirm` | `src/routes/admin/profile.identity.ts` | 每个同步检查后接绑定 |
| `POST /api/admin/pixel/key-rotation/reencrypt` | `src/routes/admin/pixelRoutes.ts` | 同步检查后绑定，并补一条失败审计 |
| `POST /api/totp/disable` | `src/controllers/totpController.ts` | 双因素会话检查后绑定 |
| `/api/totp/generate-setup`、`/verify-and-enable`、`/disable`、`/backup-codes`、`/regenerate-backup-codes` | `src/utils/securitySession.ts` 的 `requireTwoFactorConfigSession` | 共享守卫内统一加绑定判定（一次会话解析） |
| `POST /api/auth/google/bind` | `src/controllers/auth/providerHandlers.ts` | 同步检查后绑定，403 带稳定 code |
| `reveal-key` / `rotate-aes-key` / `end-sessions` / 环境变量写 | `src/routes/admin/config.ts` | 由 `requireSecuritySession` 统一完成同步 + 异步绑定 |
| `POST /api/admin/user/profile/verify` | `src/routes/admin/profile.ts` | **不加**：这是“建立安全会话”的入口，此时还没有可绑定的会话 |

避免重复查库：

- `requireSecuritySession` 只调用一次 `getSecuritySession`，把结果传给 `assertSecuritySessionBinding(req, session)`；
- `assertSecuritySessionBinding` 在 `issuedIp` 缺失或与当前 IP 相同时**直接返回**，不会触发属地查询；
- 只有 IP 变化时才走 `getCachedIpLocation` / `lookupIpLocation`（两者本身带缓存）。

## 6. 仍挂起 / 明确不做

1. **匿名入口无法按 userId 门禁**：`/api/public/deeplx`、匿名 IPFS 上传、匿名短链创建、匿名数据上报、
   OAuth `/token` / `/introspect` / `/revoke` 保持原行为。按现有契约不能回落到设备指纹；
   若要覆盖匿名流量，需要新的（非本任务授权的）判定机制。
2. **OAuth 已撤销同意的存量 refresh token**：`/token` 的 refresh grant 由客户端发起，
   当前没有 userId 上下文可查同意；本次在 `/authorize`、`/userinfo` 处拦截。
3. **RC-32 更广的敏感清单**（封号解封、赞赏审核、CDict/webhook 签名密钥、Lumen 配置、
   管理员安全配置、OutEmail 凭据）未在本轮三类范围内全部加安全会话；建议下一批按同一
   `requireSecuritySession` 模式接入。另：`GET /api/command/q` 与 `GET /api/command/history`
   只要求超管、未要求安全会话（它们不调用 `hasValidSecuritySession`，不在本次 RC-41 清单内），
   但返回的是命令队列/输出，建议后续一并评估。
4. **法律保留/取证导出**：`src/controllers/admin/legalHoldController.ts` 有自己的同步
   `requireSecuritySession`，尚无异步绑定。该文件不在本轮允许编辑范围（另一 agent 负责），
   需要该 agent 将其改为复用 `src/utils/securitySession.ts` 的实现。
5. **`adminController` 内部 403 文案**：路由层守卫已先返回稳定 code；控制器内的
   `hasValidSecuritySession` 保留为纵深防御，但其中的 403 仍无 code。因
   `src/controllers/adminController.ts` 不在允许编辑范围，未改。
6. **审计脱敏清单**：`src/utils/auditRedaction.ts` 的精确字段表里还没有
   `verificationToken`。本轮已在受影响的**路由级**审计上关掉 `reqBody` 捕获，
   但若全局 `AUDIT_LOG_CAPTURE_PAYLOADS=true`，其它带该字段的请求仍可能落库；
   建议把 `verificationtoken` 加进精确脱敏表（该文件不在本轮允许编辑范围）。

## 7. 需要协调者 / 其它 agent 应用的改动

1. **安全会话令牌的前端透传**：以下调用现在会 403 直到带上 `x-verification-token`（或 body
   `verificationToken`），需要沿用 `useSecuritySession()`：
   - `frontend/src/components/env-manager/` 里所有写 `/api/admin/envs` 的组件
     （`EcoEnchantsTokenSection`、`EcoEnchantsWebhookSection`、`MediaToolConfigSection`、
     `SecuritySecretSection` 等）与 `EnvManager.tsx` 的 `SelfContainedSecretKeySection`（短链 AES_KEY）；
   - `frontend/src/api/oauth.ts` 的 `rotateClientSecret`；
   - `frontend/src/api/pixelAdmin.ts` 的 `keyRotation.reencrypt`；
   - `RevealKeysSection` 已透传，无需改。
2. **同意面板引导**：新增门禁的页面（API Key 管理、短链管理、CDK 兑换、图片上传、TTS、DeepLX、
   转写、数据上报）需要在收到 `403 code=POLICY_CONSENT_REQUIRED` 时展示同意清单。
   现有 `FeatureConsentGate` 只在 DocConvertPage 使用；可选做法是包一层组件或在全局 403 拦截里
   派发 `POLICY_CONSENT_REQUIRED_EVENT`（参考 `frontend/src/components/docTool/DocBatchPanel.tsx`）。
3. **管理端入口**：`/api/apikeys` 现在对**所有已登录用户（含管理员）**要求 `api-access` 同意；
   若管理员账号尚未同意，Key 管理页会先要求同意。这是“开放接口以账号为责任单位”的预期行为，
   但需要产品确认管理员是否也应走同一流程。
